## 摘要

今天的 AI 开发不缺"能写代码的模型"，缺的是**"一次把方向选对"的方法**：提示词质量方差大、单模型自评有偏差、多方案比较没有证据、来回返工把 token 和时间都烧掉。PromptForge 把"人对着一个大模型反复试错"改造成一条可度量、可复现的流水线：**需求编译（关键词 → 含可执行验收标准的 SRD）→ 多候选提示词（假设不同而非措辞不同）→ 多模型并行执行 → 机器可读证据回读（测试/静态分析/性能/截图/日志）→ 异构多评委盲评 + 可执行验证 → 多准则决策（TOPSIS/Pareto，带置信区间）→ 优点融合与回归 → 预算内收敛交付**。

作品的四个创新点是：**证据驱动的多方案决策**、**异构评委去偏 + 统计置信**、**Token 预算感知的自适应编排**、**Orchestrator + Skill 双形态**（解决"外部 LLM 指挥、执行模型闷头干"的脱节问题）。对 UI、图表、演示视频等非代码产物，系统提供**可选的多模态证据通道**：用关键帧/截图 + OCR/ASR/元数据等工具提取结构化字段，写入证据包后再交给评委（详见 3.3.4）；代码类任务仍以测试、编译、静态分析为强证据。

技术上，PromptForge 站在 openJiuwen 生态（WorkSwarm/AgentOS、Agent Framework、Agent Studio、Agent System Service）与 Pangu/Qwen/DeepSeek 多模型之上，自研聚焦"需求编译、证据协议、评审去偏、MCDM 决策、预算调度"五个方法层模块；成本**算例演示（参数为假设值，非实测）** 显示：3 候选 × 2 轮 × 4 评委约 ¥1.14/任务，是单模型单轮的 6.47 倍，但只是"单模型 self-refine 长跑"的 **2.16 倍**；经济档（剪枝/弱评委/缓存/早停）可压到单轮的 **3~5 倍**（约单模型长跑的 **1.2~1.7 倍**【推断】）——对高价值任务，多方案决策在经济上成立，实际数字须以真实报价与实测替换（见附录 G）。

在首届 openJiuwen 智能体创新大赛中，本作品对应 Coding 方向，按"创意（创新性/实用性/技术可行性/场景价值）→ DEMO（完成度/用户体验/技术难度/商业价值）"两阶段准备，并已按官方时间（10-31 报名、11-10 创意、12-27 DEMO）与开源合规要求（Apache-2.0、第三方代码 ≤30%、数据安全）完成倒排。

> **一句话**：PromptForge 是 AI 开发者的"方案编译器 + 评审会"，让每个开发者都请得起一个由多个模型组成的专家评审团。

# 1. 设计目的（Why）

## 1.1 背景：AI 开发的瓶颈已经从"模型能力"转向"需求表达与方案选择"

今天的大模型已经能写代码、做设计、生成内容，但开发者仍然要花大量时间在"来回改"上：一句话需求丢给 AI，得到一版"看起来对"的方案，跑起来才发现方向不对；再补充、再修改，几轮之后 token 和时间都花掉了，最初的方案目标反而模糊了。问题的根源不在模型不够强，而在三件事：

1. **需求没有被编译**：关键词/口语需求缺少约束、验收标准和边界，模型只能猜；不同开发者的表达水平差异，直接放大为方案质量方差。
2. **方案没有被比较**：单模型单次输出没有参照系；模型"自评"又存在位置、长度、自我偏好等偏差，开发者无法判断哪条路更优。
3. **结果没有被验证**：多数提示词工具只优化文本，不知道代码能不能跑、测试过不过、性能达不达标；"提示词看起来更好"与"方案真的更好"之间没有证据链。

对 AI 开发者而言，这意味着"一次做对"很难；对非专业开发者而言，这意味着"根本问不对"。PromptForge 想解决的，正是这三件事。

## 1.2 设计目的（可判定）

| 编号 | 目的 | 判定标准（目标值需实测校准） |
|---|---|---|
| P1 | 把关键词/口语需求编译成**含可执行验收标准**的方案规格 | SRD 完整性 ≥ 0.8；验收标准 100% 可执行判定 |
| P2 | 让多个**假设不同**的方案同题竞演，而不是单模型单次输出 | 每任务 ≥ 3 个候选，候选相似度 < 0.95，假设差异可解释 |
| P3 | 用**机器可读证据 + 异构多评委**做可解释、带置信度的选优 | 推荐 Top-1 与人工评审一致率 ≥ 60%；评审 α ≥ 0.6 |
| P4 | 让成本**可见、可控、可优化**，让多方案决策在经济上成立 | 单位任务成本 ≤ 同等质量单模型试错的 1.5 倍；预算命中率 ≥ 90% |
| P5 | 让非专家也能获得专家级提示词与方案（普惠） | 新手用户首次任务可用率 ≥ 80%；澄清完成率 ≥ 80% |

> 这五条目的对应关系：P1 解决"说不清"，P2/P3 解决"选不对"，P4 解决"用不起"，P5 解决"不会用"。

大赛设四个参考方向：办公、Coding、科研、设备互联（可选一个或多个，不强制单赛道）。**本作品选择 Coding 赛道**，理由：

4. 同一套方法可低成本扩展到办公（文档/报表）与科研（文献/实验设计）方向，具备"一个作品、多场景延展"的叙事空间。

## 1.5 范围与"不做的事"

**做**：关键词→SRD 编译、多候选提示词、多模型执行、证据回读、多评委决策、融合迭代、成本账单、交付包；以及嵌入编码 Agent 的轻量 Skill 形态。

**不做（v1.0）**：不训练/微调基础模型；不替代 IDE；不做通用模型评测榜单；不做无限制自主 Agent；不做生产发布流水线接管；所有模型调用仅通过官方 API、云服务或本地部署。

**本节小结**：PromptForge 的设计目的可以压缩成一句话——**让 AI 开发从"反复试错"变成"一次选对"**；而首届 openJiuwen 智能体创新大赛的 Coding 赛道、Agent 应用定位与 openJiuwen 生态加分机制，恰好为这个目标提供了最合适的舞台。竞赛要求与设计内容的逐项对齐见 1.3.5，提交物与时间安排见第 7 章与附录 C/E。


# 2. 系统概述（What）

PromptForge 把"人对着一个大模型反复试错"改造成一条可度量、可复现的七阶段流水线：**需求编译 → 多候选提示词生成 → 多模型并行执行 → 机器可读证据采集 → 异构多评委评审 → 多准则决策与融合 → 迭代收敛与交付**。这条流水线由三类贯穿状态支撑：**需求规格 SRD**（我们到底要什么）、**证据包 Evidence Packet**（机器实际做成了什么）、**提示词版本 DAG**（每个方案是怎么演化来的）。系统提供两种形态：面向团队与跨模型的**外置编排器 Orchestrator**，以及嵌入 Codex / DSH / Claude Code 等编码 Agent 内部的**轻量 Skill**；两者共享同一套数据契约，可以单机跑，也可以混合跑。

## 2.1 一句话定位

> **PromptForge 是 AI 开发者的"提示词编译器 + 方案评审会 + 实验记录仪"**：输入关键词或一句话需求，输出一组**带执行证据、可横向比较、可解释**的高质量方案，并给出推荐项与次优备选。

类比：

| 传统软件工程 | PromptForge 对应物 |
|---|---|
| 需求文档（PRD） | 结构化需求规格 SRD（含可判定验收标准） |
| 编译器 / 中间表示（IR） | 提示词中间表示 PIR（目标、约束、上下文、验收、输出契约） |
| 多套候选实现 | 多候选提示词 Portfolio（每个候选对应一组不同的架构假设） |
| 单元测试 / CI | 执行沙箱与证据采集（测试、lint、构建、性能、截图） |
| Code Review / 评审会 | 异构多评委 + 规则评审 + 方案对比看板 |
| 版本控制 | 提示词版本 DAG（每次变异/融合都有父节点与证据） |
| 上线决策 | 多准则决策（TOPSIS / Pareto）与交付包 |

**分层职责**

| 层 | 职责 | 关键组件 | 失败时如何降级 |
|---|---|---|---|
| 交互层 | 收集需求、展示对比与决策依据、人工批注 | Web 工作台、CLI、IDE 插件、Skill | 无前端时 CLI 可用 |
| 编排层 | 状态机推进、预算与停止控制、错误恢复 | Orchestrator、任务 DAG、Token Ledger | 单轮降级为"单候选 + 规则评审" |
| 能力层 | 生成、执行、取证、评审 | 模型网关、沙箱、证据采集器、评委池 | 网关故障切换备用模型；沙箱故障转静态评审 |
| 底座层 | Agent 运行时、模型服务、算力、存储与安全 | openJiuwen WorkSwarm/AgentOS、Agent Framework、Agent Runtime、Pangu/Qwen/DeepSeek、华为云 AI 开发者空间 | 本地 Docker + 开源模型单机模式 |

> 设计原则：**编排层不直接"思考"，只做调度与仲裁**；所有判断必须落到"证据 + 规则 + 可复现的评分"上，避免变成又一个不可解释的 Agent 套壳。

## 2.3 三类贯通状态

| 状态对象 | 作用 | 生产者 | 消费者 | 生命周期 |
|---|---|---|---|---|
| **SRD**（Structured Requirement Doc，结构化需求规格） | 把模糊输入固化为可判定的目标、约束、验收标准 | 需求编译器 + 用户确认 | 候选生成器、评委、验收器 | 每次任务从 v0 开始，用户可编辑，变更留痕 |
| **Evidence Packet**（证据包） | 把"机器做出来的东西"转成可验证、可比较的结构化数据 | 执行沙箱 / 遥测采集器 / 多模态提取器 | 评委、决策器、可视化、审计 | 每个候选每次执行一份，按内容哈希寻址 |
| **Prompt DAG**（提示词版本图） | 记录候选的父代、变异说明、融合来源、评分与成本 | 编排器 | 迭代器、交付包、复盘分析 | 任务级持久化，可回放 |

这三类状态构成"单一事实源"：评委只能基于 SRD + Evidence 打分，编排器只能基于评分与预算做决策，从而把"头脑（LLM）"和"身体（执行模型）"的脱节压缩到协议层可检查的范围内（详见 3.8）。

## 2.4 术语表

| 术语 | 英文 | 含义 |
|---|---|---|
| 关键词编译 | Requirement Compilation | 把关键词/一句话需求转成含验收标准的 SRD 的过程 |
| 候选组合 | Prompt Portfolio | 一组假设不同、可并行执行的候选提示词（不是同义改写） |
| 执行契约 | Execution Contract | 每个候选必须声明的输出格式、验收命令、禁止项 |
| 证据包 | Evidence Packet | 测试结果、静态分析、构建产物、性能数据、截图/关键帧特征等结构化集合 |
| 规则评审 | Deterministic Judge | 用测试、lint、schema 校验等确定性手段打分，不依赖 LLM |
| 异构评委 | Heterogeneous Judges | 不同厂商/不同规模/不同提示模板的评审模型，用于抵消单模型偏差 |
| 一致性系数 | Krippendorff's α / ICC | 衡量多评委打分一致程度；低于阈值触发仲裁 |
| 贴近度 | Closeness Coefficient | TOPSIS 中候选与理想解的相对距离 |
| 帕累托前沿 | Pareto Frontier | 不被任何其他候选全面占优的方案集合（质量-成本-时延等） |
| 预算控制器 | Token Ledger / Budget Controller | 记录每次调用的 token 与费用，按预算分配并触发停止 |
| 双形态 | Orchestrator + Skill | 外置多模型编排器与内嵌单模型 Skill 共享同一数据契约 |

## 2.5 系统边界

**包含：**
- 关键词/一句话/仓库上下文的需求编译与澄清；
- 多候选提示词的生成、去重、多样性控制与执行契约校验；
- 多模型调用（商业 API、开源自托管、本地推理）的统一网关与路由；
- 沙箱执行、测试、静态分析、性能采集与多模态信息提取；
- 多评委评分、偏差校正、一致性检验、多准则决策、方案对比可视化；
- 优点抽取与融合、回归验证、迭代收敛；
- 交付包（SRD + 提示词 + 证据 + 评审报告 + 成本账单）导出与版本回放；
- 轻量 Skill 形态：单模型、单会话内的快速自迭代。

**不包含（至少 v1.0 不做，避免范围失控）：**
- 不训练/微调基础大模型（可作为二期用开源小模型蒸馏评审/路由模型）；
- 不替代 IDE、不直接接管生产发布流水线（只输出可审阅的交付物）；
- 不承诺"零人工"：高风险决策必须保留人工一键确认；
- 不做"无限制自主 Agent"（轮数、预算、权限均受控）；
- 不做模型能力排行或通用评测平台（只针对当前任务的方案比较）。

## 2.6 两种产品形态

| 维度 | Orchestrator（外置编排器） | Skill（内嵌轻量形态） |
|---|---|---|
| 运行位置 | 华为云/本地服务，跨会话 | Codex / DSH / Claude Code 等 Agent 内 |
| 能力范围 | 多模型、多候选、多评委、可视化、版本回放 | 单模型内循环：改写提示词 + 自检 + 返工 |
| 典型场景 | 需求评审、方案选型、团队协作、交付 | 编码过程中"随手把提示词质量拉高" |
| 成本量级 | 较高（预算可控） | 低（约 1.2~2 倍单次调用，估算，见 3.7） |
| 延迟 | 分钟级 | 秒级 |
| 数据契约 | SRD + Evidence + DAG 全量 | SRD-lite + 评分卡摘要 |
| 二者关系 | 下发"任务目标 + 验收标准 + 预算" | 回传"执行证据 + 局部优化结果" |

> **为什么必须双形态**：用户原始想法 3 的担忧是对的——如果所有判断都交给外部 LLM、执行端完全"无脑"，就会出现"头脑与身体脱节"：执行模型不知道全局目标，评审模型看不到执行细节，来回沟通把任务拖慢。解法不是二选一，而是**让执行端具备最小的自我修正能力（Skill 内循环），让外部编排器只负责跨模型、跨会话、带预算的决策（Orchestrator）**，中间用结构化协议对齐（详见 3.8）。

## 2.8 多 Agent 角色矩阵（对应官方"Agent 应用"要求）

PromptForge 不是一个"套壳聊天框"，而是由 6 个职责清晰的 Agent 组成的协同系统；每个 Agent 都可以在 openJiuwen 的 WorkSwarm / Agent Framework 上以 ReActAgent 或 WorkflowAgent 形态实现，并通过 Agent System Service 的通信总线协作：

| Agent | 职责 | 输入/输出 | 主要能力 | openJiuwen 映射 |
|---|---|---|---|---|
| 需求编译 Agent | 澄清、槽位抽取、验收标准生成 | 关键词 → SRD | 结构化输出、反问、领域模板 | WorkflowAgent + Agent Studio 工作流 |
| 候选生成 Agent | 假设矩阵采样、PIR 组装、去重 | SRD → 3~5 候选 | 提示词生成、多样性控制、自我精炼 | ReActAgent + Agent Studio Prompt 调优 |
| 执行 Agent | 网关路由、沙箱执行、证据采集 | 候选 → Evidence Packet | 工具调用、代码执行、结果结构化 | Agent Framework 工具调用 + Agent System Service 沙箱 |
| 评审 Agent | 盲评、换序、偏差校正、打分 | SRD + Evidence → Score Card | 多模型评委、评分一致性、置信区间 | 多 Agent 协同（异构模型） |
| 决策/融合 Agent | TOPSIS/Pareto、优点抽取、回归验证 | Score Card → 推荐 + 融合方案 | 多准则决策、集合覆盖、回归触发 | JiuwenSwarm 协同 + Agent 自演进 |
| 成本管家 Agent | 计量、预算分配、早停 | 全链路调用 → 账单 + 停止信号 | Token Ledger、UCB 分配、预算告警 | Agent Framework 调度 + 记忆子系统 |

> **设计要点**：Agent 之间不传"自然语言聊天记录"，只传 SRD / Evidence / ScoreCard 三类结构化对象；这样既避免上下文膨胀（呼应 WorkSwarm 的"上下文瘦身"能力），也让每一步可以独立评测与替换。

**本节小结**：PromptForge 的本质是给"提示词工程"补上软件工程的三件基础设施——可判定的需求（SRD）、可验证的证据（Evidence）、可回放的版本（DAG）；外置编排器负责"多方案决策"，内嵌 Skill 负责"单会话快速自迭代"，多 Agent 按结构化协议分工协作，整体可以运行在 openJiuwen WorkSwarm / AgentOS 之上。


# 3. 核心机制（How）

本章按"一次任务的真实流转顺序"展开：需求编译 → 候选生成 → 执行取证 → 评审聚合 → 决策与融合 → 成本控制与迭代停止 → 双形态协同 → openJiuwen 生态落地 → 安全合规。每个机制统一按**触发条件 → 处理规则 → 数据结构/公式 → 边界情况 → 与其他机制的耦合**描述。

| 阶段 | 输入 | 核心动作 | 输出 | 失败时 |
|---|---|---|---|---|
| 3.1 需求编译 | 关键词/一句话/仓库 | 槽位抽取、歧义检测、验收标准生成 | SRD v1 | 主动澄清 ≤3 问；仍不明确则拒绝开工 |
| 3.2 候选生成 | SRD | 假设矩阵采样、去重、预评审 | 3~5 个候选提示词 | 全部不合格则回到 3.1 |
| 3.3 执行取证 | 候选 + 沙箱 | 多模型并行执行、测试、采集 | Evidence Packet | 网关降级/重试；执行失败记 0 分并记录原因 |
| 3.4 评审聚合 | SRD + Evidence | 异构盲评、偏差校正、一致性检验 | 结构化评分 + 置信区间 | 一致性低则加评委/人工仲裁 |
| 3.5 决策可视化 | 评分矩阵 | TOPSIS/Pareto、对比看板 | 推荐方案 + 次优备选 | 硬约束全失败则扩大候选 |
| 3.6 融合迭代 | 方案优点 | 优点抽取、集合覆盖、回归验证 | 融合方案 vN | 融合失败回退最优单方案 |
| 3.7 成本与停止 | 全链路计量 | Token Ledger、预算调度、早停 | 成本账单 + 停止决策 | 超预算立即收口，输出当前最优 |

## 3.1 需求编译（关键词 → SRD）

**触发条件**：用户输入关键词、一句话、需求描述，或粘贴一个代码仓库作为上下文。

**处理规则（5 步）**

1. **意图分类**：新建系统 / 修改现有代码 / 方案咨询 / 代码审查 / 多媒体内容生成，不同意图走不同模板。
2. **槽位抽取**：目标（Goal）、交付物（Deliverables）、技术栈（Stack）、约束（Constraints）、验收标准（Acceptance Criteria）、非目标（Non-goals）、风险（Risks）。
3. **歧义检测**：对每个关键槽位计算"缺失度 × 影响权重"，生成待澄清问题并按"信息增益"排序。
4. **验收标准生成**：把"做好看/要流畅"这类不可判定表述翻译成可执行的代理指标（如"首屏 LCP < 2.5s""通过 12 条 Playwright 用例""p95 延迟 < 200ms"）。
5. **反向确认**：用 5 行话回显"我理解的任务 + 验收标准 + 我替你猜的部分"，用户一键确认或修改。

**SRD Schema（核心字段）**

| 字段 | 必填 | 示例 | 校验规则 |
|---|---|---|---|
| `goal` | 是 | "为校园社团做一个活动报名 Web 应用" | ≤ 80 字，含动词与对象 |
| `deliverables` | 是 | `["可运行仓库", "部署脚本", "README"]` | 至少 1 项，可验证 |
| `stack` | 否 | `["Next.js", "SQLite"]` | 不在团队规范内则提示 |
| `constraints` | 否 | "单机可跑、无外部付费依赖" | 与预算/合规规则冲突检测 |
| `acceptance` | 是 | 12 条可执行用例 + 3 条性能阈值 | 每条必须能"跑出通过/失败" |
| `non_goals` | 是 | "不做支付、不做多租户" | 至少 1 条，防止范围膨胀 |
| `ambiguity_score` | 自动 | 0~1 | > 0.2 触发澄清 |
| `open_questions` | 自动 | `[{"q":"用户规模?","impact":"高"}]` | ≤ 3 条，带默认建议 |

**公式：完整性评分与澄清阈值**

设必填槽位集合为 $S$，第 $i$ 个槽位的完成度为 $c_i \in [0,1]$，影响权重为 $w_i$（$\sum w_i = 1$），则

$$Q_{\text{srd}} = \sum_{i \in S} w_i c_i , \qquad \text{若 } Q_{\text{srd}} < 0.8 \text{ 则触发澄清}$$

澄清问题数量受控：$n_{\text{ask}} = \min(3,\ \lceil (0.8 - Q_{\text{srd}}) \times 10 \rceil)$，每题必须提供默认选项，避免"把思考成本转嫁给用户"。

**边界情况**

- 需求涉及用户无法描述的私有系统：允许上传仓库/接口文档作为上下文，SRD 中标注"基于代码推断"。
- 目标本身不可验证（"有高级感"）：必须转化为代理指标，并在 SRD 中注明"代理指标 ≠ 原目标"的风险。
- 用户拒绝澄清：按默认假设继续，但 SRD 中把假设标红，并在交付包中列出"因假设导致的返工风险"。

**与其他机制的耦合**：SRD 是 3.4 评审 Rubric 的锚点、3.6 融合冲突的裁判依据；SRD 一旦变更，已有候选标记为 `stale` 并触发重生成（可增量复用证据）。

**本节小结**：需求编译的目标不是"写得详细"，而是把需求变成**可判定的契约**；这一步做不好，后面所有评分都是在错误的目标上算分。

## 3.2 多候选提示词生成（Prompt Portfolio）

**触发条件**：SRD 确认完成，且 `ambiguity_score ≤ 0.2`。

**核心原则：候选之间是"假设不同"，不是"措辞不同"。** 同义改写的候选会让评审失去信息量，只是花钱买噪声。每个候选必须显式声明一组假设，例如：

| 假设维度 | 候选 A | 候选 B | 候选 C |
|---|---|---|---|
| 架构风格 | 单体优先，最快跑通 | 前后端分离，便于扩展 | Serverless，零运维 |
| 优化目标 | 功能正确性 | 可维护性/可测试性 | 性能/成本 |
| 实现策略 | 复用成熟模板 | 手写核心逻辑 | 引入轻量框架 |
| 验证策略 | 单元测试为主 | E2E 为主 | 压测 + 安全扫描 |
| 风险偏好 | 保守，少依赖 | 均衡 | 激进，追新 |

**生成流程**

1. **假设矩阵采样**：从 6 个假设维度中各取 1 种，用拉丁超立方/贪心覆盖挑选 $N=3\sim5$ 组差异最大的组合。
2. **PIR 组装**（Prompt Intermediate Representation）：每组假设填充为结构化提示词，固定 8 个区段——角色、目标、上下文、约束、验收标准、输出契约、示例、禁止项。
3. **多样性控制**：计算候选 embedding 两两余弦相似度；$> 0.95$ 合并，$< 0.85$ 视为有效差异；若有效差异不足，补充"反事实候选"（故意采用相反权衡）。
4. **预评审门禁**：用便宜的小模型按 4 项自检（能否直接执行、验收是否明确、边界是否覆盖、成本是否可控），低于阈值的候选先做 1 轮 self-refine 再进入执行，避免用昂贵的执行与评审成本去筛掉"提示词本身就烂"的候选。
5. **成本上限**：候选生成 token 控制在总预算的 10%~15%；$N$ 的上限由预算与 3.7 的边际收益模型共同决定。

**候选质量门禁表**

| 检查项 | 权重 | 通过标准 | 失败处理 |
|---|---|---|---|
| 可执行性 | 0.35 | 输出契约明确到文件/命令级 | 补全输出契约 |
| 验收明确性 | 0.30 | 每条验收可跑出通过/失败 | 重写验收标准 |
| 边界覆盖 | 0.20 | 至少覆盖 3 类异常输入 | 补边界用例 |
| 成本可控 | 0.15 | 预估 token 在预算内 | 压缩上下文/换小模型 |

**边界情况**：所有候选预评审均不通过 → 回到 3.1，说明 SRD 本身不可执行；若因模型能力不足，则降低候选野心（例如先做 MVP 再做扩展），而不是继续堆提示词。

**与其他机制的耦合**：候选是 Prompt DAG 的根节点；候选的假设标签会进入 3.6 的优点抽取，因为"架构风格"通常不可融合，而"测试用例、边界处理、提示词片段"可融合。

**本节小结**：多候选的价值来自"假设多样性"；没有差异的候选只是把同一个错误答案买了很多遍。

## 3.3 执行层：模型网关、沙箱与机器数据回读

### 3.3.1 模型网关（Gateway）

**定位**：统一"调用谁、怎么调、花多少、记什么账"，是用户原始想法 1 中"中转站"的工程化版本——但不是简单转发，而是**路由 + 计费 + 审计 + 降级**。

**接口**：对外统一 OpenAI-compatible 协议（`/v1/chat/completions`、`/v1/embeddings`、结构化输出），对内适配不同厂商与本地推理（Pangu/Qwen/DeepSeek 云端 API、vLLM 本地推理、OpenAI/Anthropic 兼容接口）。

**路由策略（按优先级）**

| 路由 | 规则 | 目的 |
|---|---|---|
| 能力路由 | 按任务类型查模型能力表（代码/长文/多模态/推理） | 用对的模型 |
| 成本路由 | 在满足能力阈值的模型池里选单位质量成本最低 | 省钱 |
| 延迟路由 | 交互态走低延迟小模型，后台批处理走大模型 | 体验 |
| 隐私路由 | 涉密/私有代码强制本地或专属实例 | 合规 |
| 可用性路由 | 主模型超时/限流自动切换备用模型，并记录降级原因 | 稳定 |

**必做工程细节**：幂等键防重复扣费、重试与指数退避、限流、Prompt Cache 命中统计、每次调用记录（模型、token、单价、耗时、trace_id）、失败分类（网络/限流/内容安全/格式错误）。

### 3.3.2 执行沙箱（Sandbox）

**原则**：把模型产出的代码当作**不可信代码**执行。

- 隔离：容器/微虚机，默认禁网（按需白名单），只读挂载基础镜像，工作目录可写但有配额。
- 资源：CPU/内存/磁盘/GPU 配额，墙钟超时（如 10 分钟），进程数限制。
- 标准化动作：`install → build → test → lint → type-check → benchmark → render/screenshot`，每步产出结构化结果。
- 可复现：记录镜像哈希、依赖锁文件、随机种子、环境变量（脱敏）。
- 安全：依赖安装走内网镜像；禁止 `sudo`、禁止访问宿主机路径；执行日志脱敏后入库。

### 3.3.3 证据包（Evidence Packet）

**定义**：每个候选每次执行产出一份 JSON 证据包，是评委唯一被允许使用的"事实输入"（评委可以看代码 diff，但不能凭空想象运行结果）。

| 证据组 | 字段示例 | 强度 |
|---|---|---|
| 可执行验证 | `tests.passed / total / coverage`、`build.status`、`typecheck.errors` | 强 |
| 静态质量 | `lint.errors/warnings`、`complexity`、`duplication`、`sast.findings` | 中强 |
| 性能 | `latency.p50/p95`、`memory.peak`、`bundle.size` | 中 |
| 安全 | `dependency_vulns`、`secret_scan`、`permission_scope` | 中强 |
| 多模态 | `screenshots[]`、`video.keyframes[]` 的描述/OCR/ASR、`ui_diff` | 中 |
| 差异 | `diff.files/lines/hunks`、`churn` | 中 |
| 成本 | `tokens.input/output`、`usd.estimate`、`wall_time` | 强 |
| 可复现 | `image_hash`、`lockfile_hash`、`seed` | 强 |

**证据冲突处理**：不同证据组给出矛盾信号时（例如"测试通过但安全扫描高危"），按硬约束优先：安全/合规失败直接一票否决；测试失败进入观察区；性能不达标按权重扣分。

### 3.3.4 多模态与工具证据（可选能力）

对于 UI、图表、演示视频、扫描文档等"非代码"产物，系统提供**可选**的多模态证据通道；该通道默认关闭，仅在任务确实涉及视觉/媒体内容时启用：

| 层级 | 做法 | 适用场景 | 成本口径 |
|---|---|---|---|
| 关键帧/截图 | 抽取关键帧或界面截图，交多模态模型理解 | UI 还原、图表解读、演示内容摘要 | 按供应商官方 token 计费口径；参考量级：OpenAI 高细节 1024² 图片约 765 token、Claude 同尺寸约 1.4k token（官方文档口径，实际以当时文档为准） |
| 工具提取 | ffprobe 读元数据、OCR 读字幕、ASR 转写、CV 检测、UI 自动化截图对比 | 需要结构化描述的视频/图像 | 本地工具运行成本，可忽略 token |
| 结构化回读 | 工具结果写入 Evidence Packet（`screenshots[]`、`ui_diff`、`ocr_text`、`asr_text`、`media_meta`） | 评委据此评审 | 与代码证据同流程 |

**使用原则**

- 多模态证据属于"中证据"，用于 UI/体验/内容类主观维度；代码类任务仍以测试、编译、静态分析为强证据。
- 只把"必要关键帧 + 工具提取的结构化摘要"送入模型，控制上下文长度与成本；默认抽 6~10 张关键帧（按官方 token 口径估算约 0.5 万~1.4 万 token，实际以分辨率、帧数与供应商口径为准）。
- 视频类任务默认组合"关键帧 + ASR 字幕 + 元数据"；复杂视频应拆解为可验证子任务（截图对比、字幕校对、操作步骤校验）。
- 涉及隐私/敏感内容时先脱敏再送模型；默认走本地工具，必要时使用本地多模态模型。

**边界**：多模态评审不承诺"理解任意视频"；它只补充视觉/内容维度的证据，不能替代可执行验证。是否启用由任务分类器与用户配置共同决定。

**本节小结**：执行层是 PromptForge 与"纯提示词工具"的分水岭——只有真正把代码跑起来、把结果结构化，评审才有事实依据；对图像/视频类产物，用"关键帧 + 工具提取 + 结构化回读"补充证据，作为可选能力按需启用。


## 3.4 评审聚合与偏差校正

> **数据说明**：3.4–3.7 中的数字均为【算例】（人为构造的参数与结果，仅用于演示公式与计算步骤），不代表任何实测效果。落地时所有参数须以实际测量替换，并登记在附录 G 的数据台账中。

### 3.4.1 评审协议（先定协议，再谈数学）

- **评分制式**：日常用 1–5 分绝对分 rubric（成本低、可跨候选比较）；当 Top-2 差距小于噪声时，切换为**成对比较 + 位置互换**（更可靠，但比较次数随候选数平方增长）。
- **Rubric 固定**：评审前确定评分维度与锚点，评审中不允许改 rubric；每条评分必须"先引用证据，再给分"。
- **盲评**：隐藏候选来源与生成模型；候选呈现顺序随机化；成对比较做 A/B 与 B/A 两遍，用于估计位置偏差。
- **异构评委**：$K=4$（至少覆盖 2 个模型家族），评委尽量与候选生成模型不同家族；**任何评委不得评审自己参与生成的候选**。
- **机器可读输出**：`{"candidate_id", "criterion", "score", "evidence_refs", "rationale", "confidence"}`，方便聚合与审计。

> 【算例估算】在最常见的 3 候选 × 2 轮 × 4 评委配置下（参数见 3.7.3 假设表），成对比较（16 次）与绝对评分（20 次）成本几乎相同（+2.9%），只有做位置互换才翻倍；因此"单轮单顺序的成对比较"是控制尺度漂移最便宜的手段，位置互换只对差距 < 0.2 分的近邻对启用。该比例随单价与 token 画像变化，实测前不作为结论。

### 3.4.2 标准化与去极值（不能省的一步）

**评委内标准化**（消除不同评委的打分尺度差异）：

$$z_{kj}=\frac{s_{kj}-\mu_k}{\sigma_k},\qquad \hat{s}_{ij}=\frac{\sum_k \omega_k z_{kj}}{\sum_k \omega_k}$$

$K=4$ 时先去一个最高分、一个最低分取中间两个的均值（trimmed mean）；$K\ge5$ 用中位数或 MAD 剔除离群值。**直接把原始分平均，等于让打分尺度不同的评委按噪声加权。**

**算例（3 候选 × 4 评委，0–10 分）**

| 候选 | J1 | J2 | J3 | J4 | 原始均值 | 去极值均值 | 排序 |
|---|---|---|---|---|---|---|---|
| A | 8.0 | 8.5 | 8.4 | 8.2 | 8.275 | 8.300 | 2 |
| B | 9.0 | 9.2 | **5.0** | 8.8 | 8.000 | **8.900** | **1** |
| C | 7.5 | 7.8 | 7.6 | 7.7 | 7.650 | 7.650 | 3 |

J3 给 B 的 5.0 是离群低分（J3 对 A/C 打分正常），一个极端值让 B 从第 1 掉到第 2——**排序反转换来的是"多花一份执行成本去优化一个错误结论"**，所以去极值必须先做。

### 3.4.3 Bradley-Terry / Elo 聚合

**Bradley-Terry**（离线批量、多评委、多轮）：候选 $i$ 战胜 $j$ 的概率

$$P(i \succ j)=\frac{\theta_i}{\theta_i+\theta_j}$$

用 MM 迭代求解（数值稳定、无需梯度）：$\theta_i \leftarrow W_i / \sum_{j\ne i} n_{ij}/(\theta_i+\theta_j)$，再归一化，直到收敛。**算例**：4 候选、每对比较 8 次，MM 收敛得 $\theta=(A:0.495,\ C:0.213,\ B:0.186,\ D:0.106)$。注意 B 与 C 胜场只差 1，$P(C\succ B)=0.534$——**这类"弱排序"不能当结论**，应作"两者进入下一轮"的依据。

**Elo**（在线增量、多轮）：$E_{ij}=1/(1+10^{(R_j-R_i)/400})$，$R_i\leftarrow R_i+K(S_{ij}-E_{ij})$；多评委取票面平均，多轮用 $K_t=K_0/(1+t/\tau)$ 递减。离线报告用 BT，实时看板用 Elo，二者都要用 bootstrap 给排序置信区间。

### 3.4.4 一致性检验与低一致性处理

| 指标 | 可用 | 勉强可用 | 不可用 |
|---|---|---|---|
| Krippendorff's α | ≥ 0.80 | 0.667–0.80（探索性） | < 0.667（< 0.5 必须停工） |
| Cohen/Fleiss κ | ≥ 0.61 | 0.41–0.60 | ≤ 0.40 |
| ICC(2,k) | ≥ 0.75 | 0.50–0.75 | < 0.50 |

**每个指标分别算一致性**（质量指标可能一致性高、可维护性可能低），并给 bootstrap 置信区间。低一致性时按根因处理：

| 根因 | 诊断 | 处理 |
|---|---|---|
| rubric 模糊 | 分项一致性都低、理由不引用同一标准 | 拆子项 + 给 3 个锚点示例，重跑受影响评分 |
| 评委尺度不同 | 评委均值/方差差异大 | 评委内 z 标准化，或改秩/成对比较 |
| 单个离群评委 | leave-one-out α 明显上升 | 降权或剔除，记录并复核该评委 prompt/模型 |
| 指标本身主观 | 硬指标一致、软指标不一致 | 软指标降权，主决策只用高一致性指标 |
| 系统偏差 | 位置互换分差大、长度与得分相关 | 先做 3.4.5 校正，再算一致性 |
| 仍 < 0.5 | 所有手段无效 | 停止采信该指标；只用可执行验证，文档明示不确定性 |

### 3.4.5 偏差校正

- **位置偏差**：同一对候选按 A/B 与 B/A 各评一次，$b_{pos}=\text{mean}(s_{AB}-s_{BA})$，校正分取 $(s_{AB}+s_{BA})/2$；$|b_{pos}|>0.3$（0–10 分制）的评委降低成对结论权重。
- **自我偏好**：跨模型家族评委 + 匿名化 + 评委不评自己生成的候选；评委家族在评审池占比 ≤ 1/3。
- **长度偏差**：$s=\beta_0+\beta_1\ln(\text{len})+\varepsilon$，用残差 $\varepsilon$ 作为去长度后的质量分；或把长度差作为 BT 协变量：$\text{logit}P(i\succ j)=\theta_i-\theta_j+\beta^\top(x_i-x_j)$。
- **评审放大风险**：反复用评委分数选优会"先升后降"（reward overoptimization），因此**硬验证信号优先 + 最多 3 轮 + 早停**，不追求"把评委分刷到最高"。

**本节小结**：评审层的可靠性不是靠"多叫几个模型"，而是靠协议（盲评、异构、换序）、统计（标准化、去极值、一致性、置信区间）与硬证据三重保障；三者缺一，多评委就会变成"多花钱买噪声"。

## 3.5 多准则决策与对比可视化

### 3.5.1 指标体系、归一化与权重

**两层指标树**（一级 4 个）：

| 一级指标 | 权重（均衡预设） | 二级指标 | 测量口径 |
|---|---|---|---|
| 质量 Q | 0.45 | 正确性 0.50 / 完整性 0.25 / 可维护性 0.15 / 安全性 0.10 | 可执行验证通过率 + rubric；安全性为一票否决型 |
| 效率 E | 0.15 | 时延 0.40 / Token 消耗 0.60 | p50/p95 端到端秒数；每任务 input+output token |
| 成本 C | 0.20 | 单位任务成本 | ¥/任务（执行 + 评审 + 验证） |
| 稳定性 S | 0.20 | 稳定性 | $1-\sigma/\mu$（重复运行），失败率打折 |

**三套预设权重**（可配置）：A 均衡 `(0.30, 0.20, 0.20, 0.15, 0.15)`（正确性/完整性/成本/时延/稳定性，用于演示算例）；B 生产 7 维多级；C 成本敏感 `(0.25, 0.15, 0.35, 0.15, 0.10)`。

**归一化**：效益型 $y=(x-x_{min})/(x_{max}-x_{min})$；成本型反向；目标型/区间型按 SLO 衰减；重尾先 $\ln(1+x)$ 或秩归一。**基准必须固定**（需求基线/SLO/历史最优），不能取"本批候选的 min/max"，否则候选整体变差时仍会产出 1.0 分，且跨轮不可比。

**权重确定**：AHP 主观权重（$CR<0.1$）+ 熵权法客观权重 + 组合 $w=\alpha w^{subj}+(1-\alpha)w^{obj}$（$\alpha=0.6$）。**敏感性**：对每个权重 ±0.05 扰动重算排序，Kendall τ ≥ 0.8 才采纳；τ 低说明结论对权重敏感，必须回到需求方协商，不能默默取平均。

### 3.5.2 TOPSIS：步骤与算例

```
Step 1 向量归一化 r_ij = x_ij / sqrt(Σ_k x_kj²)
Step 2 加权矩阵 v_ij = w_j · r_ij
Step 3 正/负理想解（效益型取最大/最小，成本型取最小/最大）
Step 4 欧氏距离 D_i⁺、D_i⁻
Step 5 贴近度 C_i = D_i⁻ / (D_i⁺ + D_i⁻)
Step 6 C_i 越大越优；并列比较 D_i⁺
```

**算例（4 候选 × 5 指标，权重取预设 A）**

| 候选 | 正确性 | 完整性 | 成本(¥) | 时延(s) | 稳定性 | 贴近度 C* | 排名 |
|---|---|---|---|---|---|---|---|
| A | 82 | 76 | 38 | 42 | 0.88 | 0.5230 | 3 |
| B | 90 | 68 | 52 | 35 | 0.80 | 0.4008 | 4 |
| C | 74 | 88 | 26 | 55 | 0.92 | **0.5642** | **1** |
| D | 86 | 80 | 45 | 30 | 0.76 | 0.5253 | 2 |

**解读（比结果更重要）**：

1. C 胜在"成本最低 + 完整性/稳定性最高"，但**正确性垫底（74）**——若正确性有硬门槛（如 ≥80），C 应在排序前被硬约束过滤，TOPSIS 只是排序器，不负责守门；
2. A 与 D 的贴近度只差 0.0024（0.46%），小于评委噪声量级，**不能宣布 A 优于 D**；应做 bootstrap 秩稳定性检验，不稳定则并列进入下一轮；
3. 排序结论必须附"硬约束过滤 → Pareto 剪枝 → 排序 → 稳定性检验"的完整链条，而不是只报一个 TOPSIS 分数。

### 3.5.3 Pareto 前沿与超体积（HV）

**支配关系**：$a$ 支配 $b$ 当且仅当所有目标上 $a$ 不差于 $b$ 且至少一项严格更好；非支配集合即 Pareto 前沿。**作用**：权重未定时先剔除严格更差的候选，零信息损失。

**超体积**（成本最小化、质量最大化，参考点 $r=(c_{ref},q_{ref})$，前沿按成本升序）：

$$HV=\sum_{i=1}^{L}(c_{i+1}-c_i)(q_i-q_{ref})$$

**算例**：6 个候选 (成本, 质量)，非支配集 {E(30,0.80), G(40,0.84), F(45,0.86), H(55,0.88)}，参考点 (60,0.75)，$HV=2.70$；新增候选 K(42,0.87) 支配 F 后 $HV'=2.89$，**ΔHV=+7.04%**。

**HV 的三个用途**：① 每轮只把前沿候选送入下一轮；② ΔHV < 1% 作为"再加候选/再加轮"边际贡献低的停止辅助信号；③ 对外报告"预算–质量前沿"比只报冠军更诚实。

### 3.5.4 加权和（SAW）vs TOPSIS

- **SAW**：$S_i=\sum_j w_j y_{ij}$，线性补偿、透明、与期望效用一致；缺点是一项极差可被其他高分补回。
- **TOPSIS**：与正/负理想解的相对距离，对"单项崩盘"惩罚更重，但结果依赖候选集（增删候选可能秩反转）。

**反转示例**（等权 3 指标）：X=(10,10,1)，Y=(6,6,6)；SAW 归一化后 X=0.667>Y=0.333，而 TOPSIS 下 X 因第三项远离正理想解，$C_X=0.371<C_Y=0.629$——**方法选择本质是价值取向，不能挑一个好看的结果**。

**默认组合拳（直接实现）**：硬约束过滤 → Pareto 前沿压到 2–3 个 → TOPSIS 定序 → bootstrap 秩稳定性 → Top-1 不稳定则前二并列进下一轮；SAW 全程作为交叉校验同步计算，两者 Kendall τ 写入日志。

### 3.5.5 对比可视化与"会议模式"

| 视图 | 内容 | 回答的问题 |
|---|---|---|
| 雷达图 | 各候选在 6~8 个指标上的归一化得分 | 谁强在哪、短板在哪 |
| 成本–质量散点（带 CI） | 横轴总成本、纵轴质量分，误差棒 + Pareto 前沿 | 多花的钱值不值 |
| 评委–候选热力图 | 每个评委对每个候选的 z 分 | 谁在分歧、分歧多大 |
| 桑基图 | 生成/执行/评审/融合/回归的成本流向 | 钱花在哪 |
| 并排 diff | 候选提示词与产出代码的差异 | 方案到底差在哪 |
| 争议点标注 | 一致性低或 CI 重叠的维度高亮 | 需要人工讨论哪里 |

**本节小结**：决策层的目标不是"算出一个冠军"，而是**让选择过程可解释、可复现、可辩论**：硬约束守门、Pareto 去噪、TOPSIS 定序、统计检验防误判、可视化让团队把分歧说清楚。

## 3.6 融合与迭代

### 3.6.1 把"优点"原子化

融合的本质不是"把两份提示词拼起来"，而是抽取**可合并的优点原子（atom）**再组合：

$$\text{atom}_k=(\text{id},\ \text{描述},\ \text{来源候选},\ \text{收益 }u_k,\ \text{成本 }c_k,\ \text{证据},\ \text{依赖/冲突集合})$$

- $u_k$：预期质量提升（0–1 质量点，优先用历史 A/B 效应量；无证据的条目打 0.5 折）；
- $c_k$：合并成本（复杂度/预算单位或 token）；
- 抽取流程：LLM 读评审理由 + 通过/失败用例 → 输出 atom JSON → 规则抽检 → 语义去重（相似度 > 0.85 合并）。

### 3.6.2 融合建模：集合覆盖 + 预算背包

**加权集合覆盖**（用最少成本覆盖所有必需优点 $R$）：

$$\min\sum_k c_k y_k \quad \text{s.t.}\ \sum_{k:e\in A_k} y_k\ge 1,\ \forall e\in R;\ y_k\in\{0,1\}$$

NP-hard，贪心按"新增覆盖收益/成本"取最大，近似比 $1-1/e$；条目少时直接 ILP 精确解。**算例**：必需覆盖 {e1 JSON, e4 自检, e5 引用, e7 拒答}，贪心选 P3(覆盖 e1/e4/e7, 成本 0.9) + P4(覆盖 e5, 成本 0.6) = **1.5**，且穷举验证为最优。

**冲突感知 0–1 背包**（预算内收益最大）：

$$\max\sum_k u_k y_k \quad \text{s.t.}\ \sum_k c_k y_k\le B;\ y_k+y_l\le 1,\ \forall(k,l)\in\text{Conflict};\ y_k\le\sum_{l\in dep(k)}y_l$$

**算例**：8 条优点、预算 B=8，无冲突最优 {e1,e2,e3,e6,e7}，收益 35、成本 8；若 e1（纯 JSON 输出）与 e4（展示思维链自检）互斥且 e4 为硬需求，最优变为 {e2,e3,e4,e7}，收益降为 **30**（相对全局最优损失 5；若只是"e4 必选但 e1 可共存"，最优 {e1,e2,e4,e7} 收益 32，损失 2）——**冲突的代价必须显式报告给决策者**，不能偷偷丢掉一个优点。

### 3.6.3 冲突检测与消解

| 冲突类型 | 例子 | 处理 |
|---|---|---|
| 输出契约 | "只输出 JSON" vs "展示推理" | 拆两阶段调用/条件分支输出 |
| 指令矛盾 | "必须先反问" vs "禁止反问" | 按优先级取一，或改条件指令 |
| 长度/预算 | "详细展开" vs "≤200 字" | 上限优先，或按任务类型切模板 |
| 安全策略 | 越狱式角色扮演 vs 拒答策略 | P0 硬约束，直接剪掉 |
| 重复冗余 | 两条都要求"标注不确定性" | 语义去重保留收益大者 |
| 顺序依赖 | 先自检再输出 vs 单次生成 | 依赖图拓扑排序，无法满足则降级 |

流水线：规则过滤（快）→ 语义相似度/NLI（中）→ LLM 判别给证据（慢，仅高风险对）→ 人工复核（安全/合规类）；输出冲突图，按最大权重独立集选可并存条目，再进背包。

### 3.6.4 融合后强制回归验证

**回归集**：固定 golden set（30~100 条，覆盖主任务 + 边界 + 安全用例），融合版与每个原候选做配对比较。

- **McNemar 检验**：$b$=融合通过且基线失败，$c$=融合失败且基线通过，$\chi^2=(|b-c|-1)^2/(b+c)$（df=1，临界 3.84）；小样本用精确二项检验。
- **算例**（30 条）：情形 1，b=6、c=3 → $\chi^2=0.444<3.84$，$p=0.254$，**不显著，不能宣称融合更好**；情形 2，b=8、c=1 → $\chi^2=4.0>3.84$，$p=0.0195$，**显著，可采纳**。
- **三条门同时满足才发布**：① 质量非劣（非劣性边界 ε=2 个百分点，bootstrap CI）；② 成本 ≤ 单任务预算；③ 安全/格式零回归（任何一条安全用例回归直接拒绝）。
- **回滚**：保留候选版与融合版双份 prompt，线上影子流量出现回归可一键回滚，日志记录融合版本号与 atom 来源。

### 3.6.5 迭代、变异与版本 DAG

- **变异**：针对评审指出的短板改条件/补边界/换实现假设（每次只改 1~2 个变量，保证可归因）；
- **交叉**：把两个候选的可融合优点组合成新候选；
- **剪枝**：每轮只保留 Pareto 前沿 + 多样性代表，$N_{t+1}=\max(N_{min},\lceil\rho N_t\rceil)$，$\rho=2/3$；
- **版本 DAG**：每个节点记录父节点、变异说明、证据包、评分、成本；支持任意历史版本回放与交付包重建；
- **上限**：默认最多 3 轮，收益递减或预算不足即停（见 3.7.5）。

**本节小结**：融合是"高风险、高回报"的可选动作：只有结构化优点、显式冲突代价与严格回归检验三者齐备时才做；否则老老实实交付最优单方案，反而是更专业的选择。


## 3.7 成本模型与停止准则

### 3.7.1 单轮成本公式

设生成/执行/评委模型单价分别为 $(u^{g}_{in},u^{g}_{out})$、$(u^{e}_{in},u^{e}_{out})$、$(u^{r}_{in},u^{r}_{out})$（元/token），token 画像分别为 $T^g_{in},T^g_{out}$、$T^e_{in},T^e_{out}$、$T^r_{in},T^r_{out}$，任务数 $m$，候选数 $N_t$，评委数 $K_t$，可执行验证成本 $C_{verify}$：

$$C_{round}(t)=\underbrace{N_t(u^g_{in}T^g_{in}+u^g_{out}T^g_{out})}_{\text{候选生成}}+\underbrace{N_t m(u^e_{in}T^e_{in}+u^e_{out}T^e_{out})}_{\text{执行}}+\underbrace{N_t K_t(u^r_{in}T^r_{in}+u^r_{out}T^r_{out})}_{\text{评审}}+C_{verify}(N_t)$$

### 3.7.2 多轮递推与缓存

$$C_{total}=\sum_{t=1}^{T}C_{round}(t)+C_{fuse}+C_{reg},\qquad N_{t+1}=\max\left(N_{min},\lceil\rho N_t\rceil\right)$$

带缓存（命中率 $h$，缓存价比例 $\eta$）的有效成本：$C_{eff}(x)=x\cdot u\cdot[1-h(1-\eta)]$；批处理折扣：$C_{eff}=C(1-\gamma_{batch})$。

### 3.7.3 成本算例演示（参数为假设值，非实测）

> **【算例】** 以下单价与 token 画像为演示参数，仅用于说明计算过程，不代表真实报价或实测消耗；实际值须以供应商报价与实测 token 替换（登记于附录 G 数据台账）。

**【示例假设】** 强模型 ¥2/¥8 每百万 token（输入/输出），弱模型 ¥0.5/¥1.5；生成 800/1200 token、执行 2500/1500、评分 2200/150、成对比较 3200/100；$m=10$，$N_1=3$，$\rho=2/3$，$K=4$，$T_{max}=3$。价格量级参照 2026-10-20 DeepSeek 官方价（flash：缓存命中输入 0.02–0.04 元/M、未命中 1–2 元/M、输出 4–8 元/M，空闲半价；v4-pro：0.15–0.30 / 4.5–9.0 / 13.5–27 元/M），仅为量级对照，落地时按实际报价替换。

**基线（单模型、单轮、单候选、1 评委）**：执行 ¥0.1700 + 评审 ¥0.0056 = **¥0.1756/任务**。

**多方案（2 轮 + 融合 + 回归）**：

| 组成 | 成本 | 占比 |
|---|---|---|
| 轮 1（N=3, K=4）：生成 0.0336 + 执行 0.5100 + 评审 0.0672 | ¥0.6108 | 53.8% |
| 轮 2（N=2, K=4）：生成 0.0224 + 执行 0.3400 + 评审 0.0448 | ¥0.4072 | 35.8% |
| 融合（1 次 3000/2000 token） | ¥0.0220 | 1.9% |
| 回归验证（5 任务 × 执行 + 2 评委） | ¥0.0962 | 8.5% |
| **合计** | **¥1.1362** | 100% |

**成本倍数**：相对单模型单轮 **6.47×**；**但相对"单模型 self-refine 跑 3 轮"（¥0.5268）只有 2.16×**——这是对用户"多方案会不会贵到接近集群模式"担忧的正面回答：**贵的不是多评委，而是"每个候选都要把全部任务跑一遍"**。

**结构洞察**：轮内执行占 83.5%，评审仅 11.0%，生成 5.5%。所以优化优先级是：

| 优化项 | 效果 | 优先级 |
|---|---|---|
| 候选剪枝（第 2 轮 N=1） | 总成本 −17.9% | ★★★★★ |
| 执行前缀缓存（h=0.7, η=0.2） | 总成本 ≈¥0.9602（−15.5%）【推断】 | ★★★★☆ |
| 早停（少跑轮次） | −10%~20%【推断】 | ★★★★☆ |
| 弱模型/异构评委 | 总成本 −7.5% | ★★★☆☆（不要先砍，多评委是置信度来源） |
| 弱评委 + 剪枝组合 | −23.9% | ★★★★★ |

综合缓存、剪枝、早停、级联、批处理等，经济档可把总成本压到单轮的 **3~5 倍**（相对 6.47× 降低约 40%~55%；换算成单模型长跑约 1.2~1.7 倍，均为【推断】，需 A/B 实测校准），具体见 3.7.4 与 3.7.6。

### 3.7.4 预算分配：多臂老虎机与实用策略

把"每个候选"视为一个臂，拉动 = 安排一次比较/评分，奖励 = 该候选获胜。**成本感知 UCB**：

$$i^*=\arg\max_i\ \frac{\mu_i+\sqrt{2\ln n/n_i}}{cost_i}\quad\text{或等价地}\quad score_i=\mu_i+\sqrt{2\ln n/n_i}-\lambda\cdot cost_i$$

**Thompson Sampling（预算版）**：对每个候选维护 $\text{Beta}(\alpha_i,\beta_i)$，每轮抽样 $\theta_i\sim\text{Beta}(\alpha_i,\beta_i)$，选 $\max\theta_i$ 的候选安排比较，观测胜负更新参数，每 8 次重算 $P(best)$，≥0.95 即停。

**实用分配**：冷启动每臂至少 2 次（占预算约 20%）；主分配集中到 Top-2 与挑战者；每 10 次强制给最冷门臂 1 次（防早熟）；Top-2 差距 < 噪声时只在两者间加评（配合位置互换）；预算不足一轮时直接输出 Top-1 + 置信度。

### 3.7.5 停止准则

每轮结束计算 5 个信号：剩余预算 $B_{rem}$、后验 $P(best)$、相邻轮分数变化 $\Delta_t$、排序稳定性 $\tau_t$、SPRT 状态。停止条件（满足任一，但必须区分"确信停"与"预算停"）：

$$\text{STOP}:= \big(P(best)\ge 0.95\big)\ \lor\ \big(B_{rem}<C_{next}\big)\ \lor\ \big(t\ge T_{max}\big)\ \lor\ \big(|\Delta_t|<\delta\ \text{且}\ |\Delta P|<\delta\ \text{连续 2 轮且}\ \tau_t\ge 0.9\big)$$

- **置信停**：输出 Top-1 + 后验概率 + 置信区间；
- **预算停/轮数停**：输出 Top-1 + **未决清单**（Top-2 差距、达到 0.95 还需多少预算估计），并标注"未达置信阈值"；
- **支配停**：某候选 Pareto 支配其余且差距 > 噪声，直接跳过剩余轮；
- **失败停**：硬约束全部失败（无候选通过安全/格式门），报警并回退人工规则，不输出"最优"。

**Beta-Bernoulli 后验算例**（3 候选，每轮每候选新增 6~8 次成对比较）：

| 轮次 | 后验 (A,B,C) | P(A best) | P(B best) | 决策 |
|---|---|---|---|---|
| R1 | Beta(10,4), Beta(8,6), Beta(5,9) | 0.787 | 0.202 | 继续 |
| R3 | Beta(21,7), Beta(16,12), Beta(8,20) | 0.926 | 0.074 | 继续 |
| R4 | Beta(28,8), Beta(20,16), Beta(9,27) | **0.980** | 0.020 | **停止，A 胜出** |

**SPRT 算例**（挑战者优势 p₁=0.75 vs p₀=0.5，α=0.05，β=0.20）：接受 H1 边界 $\ln((1-\beta)/\alpha)=\ln16=2.7726$；n=16、k=13 时 $\Lambda=3.19>2.77$ → 停止接受"挑战者更优"；Wald 近似期望样本量仅约 16.4（H1 下），少于固定 24 次的均匀方案。

**默认参数**：$T_{max}=3$、$\delta=0.01$、$\tau\ge0.9$、$P(best)\ge0.95$（高风险任务可提到 0.99）、α 阈值见 3.4.4。

### 3.7.6 与"单一大模型长时间集群式跑"的对比框架

用户担心"来回联动的 token 会追上集群模式"。正确的比较对象不是"单轮"，而是"单模型 self-refine 长跑"：

$$C_A=\sum_t\big[N_tG+N_t mE+N_tK_tR\big]+Fuse+Reg,\qquad C_B=T_b\,mE_B+T_bR_B+\text{重试成本}$$

**质量模型**（需实测标定，不可直接外推）：$Q_A(N,T)=Q^A_\infty-a_AN^{-\gamma_A}$，$Q_B(T_b)=Q^B_\infty-a_BT_b^{-\gamma_B}$。

**选优判据**（三选一，按场景）：

1. 预算约束下最大化质量：$\arg\max Q\ \text{s.t.}\ C\le B$；
2. 质量门槛下最小化成本：$\arg\min C\ \text{s.t.}\ Q\ge Q_0$；
3. 增量收益 > 机会成本：**当且仅当** $(Q_A-Q_B)V>C_A-C_B$ **时选多方案**（$V$ 为质量点价值，可由返工人力/时间折算）。

**多候选更优的条件**：任务存在多个合理解法；单模型自迭代 2 轮内接近饱和；候选差异能被评委稳定区分（α ≥ 0.8）；质量增益价值超过约 2.16× 的成本差。**单模型长跑更优的条件**：唯一正确答案、多样性收益低；预算极紧/延迟敏感；评委一致性 < 0.75（多花钱买噪声）。**公平比较四条硬要求**：等 token 预算、等任务集、同一评测协议、报告置信区间；并做两个消融（多候选 vs 同候选多采样；多评委 vs 单评委多次）。

**本节小结**：成本模型给出的结论不是"多方案便宜"，而是"**多方案的钱主要花在执行上，所以剪枝、缓存、早停的收益最大；评委不能先砍，评审是置信度的来源**"；对用户而言，产品必须按任务价值分档，而不是所有任务都开满。

## 3.8 双形态架构：Skill 与 Orchestrator 的分工（解决"头脑与身体脱节"）

### 3.8.1 脱节从哪里来

用户原始想法 3 的担忧是对的：如果"外部 LLM 只负责写提示词、执行模型只负责干活"，会出现四个断点：

| 断点 | 表现 | 后果 |
|---|---|---|
| 目标不一致 | 外部 LLM 不知道执行模型的上下文窗口/工具限制 | 提示词"看起来专业"，执行不了 |
| 上下文不同步 | 执行模型的中间状态不回传或回传成自然语言 | 评审只能凭想象打分 |
| 反馈不结构化 | 执行结果散落在聊天记录里 | 无法比较、无法复现 |
| 责任边界不清 | 两边都能"改需求"，没有唯一事实源 | 来回甩锅、任务拖沓 |

### 3.8.2 双形态分工与数据契约

| | Skill（内嵌） | Orchestrator（外置） |
|---|---|---|
| 定位 | 执行端"最小自我修正" | 跨模型"决策与仲裁" |
| 职责 | 改写提示词 → 自检 4 项 → 最多 2 轮返工 | 需求编译、多候选、多模型执行、评审、决策、融合 |
| 状态 | SRD-lite（目标 + 验收摘要） | SRD 全量 + Evidence + ScoreCard + Prompt DAG |
| 协议 | 工具调用 / Skill 包（可复用 Skill Hub） | MCP（工具接入）+ A2A（Agent 委派）+ REST |
| 输出 | 改进后的提示词 + 自检结论 | 交付包（方案 + 证据 + 评审报告 + 成本账单） |
| 成本 | 约 1.2~2× 单次调用（估算） | 算例约 2.16× 单模型长跑；经济档约 1.2~1.7×【推断】 |

**关键设计**：编排器**只做三件事**——定义目标与验收（SRD）、分配预算、仲裁分歧；执行端 Skill **拥有**"在单会话内怎么改"的自主权。两者之间只传结构化对象，不传"你觉得怎么样"这种自然语言寒暄。这样"头脑"不越权指挥细节，"身体"不会脱离目标乱跑。

### 3.8.3 模型调用的合规与数据边界

模型获取遵循"官方渠道、可审计、数据可控"三条原则：

| 维度 | 规则 |
|---|---|
| 调用渠道 | 仅通过官方 API / 云服务（Pangu、Qwen、DeepSeek 等）或本地部署模型调用；不接入非官方页面、逆向接口或未授权渠道 |
| 数据流向 | 记录每次调用的数据流向与保留策略；敏感代码/数据默认只走本地或专属实例，传输前脱敏 |
| 成本记录 | 记录模型、版本、单价、token 与费用，写入 Token Ledger；价格变更时同步更新台账 |
| 账号与额度 | 使用组织/个人正式账号与官方计费方式，遵循服务条款；不使用来源不明的额度或代理 |
| 降本手段 | 模型路由、前缀缓存、批处理、本地小模型初筛、候选剪枝与早停；成本优化不牺牲合规与数据安全 |

### 3.8.4 形态选择决策表

| 任务特征 | 推荐形态 | 理由 |
|---|---|---|
| 单轮小改动、延迟敏感 | Skill | 秒级、低成本 |
| 多文件/多方案/需评审 | Orchestrator | 需要证据与统计决策 |
| 涉密/私有代码 | 本地 Orchestrator + 本地模型 | 数据不出域 |
| 演示/答辩 | Orchestrator + 缓存回放 | 稳定、可解释 |
| 批量任务 | Orchestrator 经济档 + 批处理 | 成本优先 |

**本节小结**：双形态不是"两个产品"，而是"同一套协议的两个执行位置"：Skill 负责让执行端不脱节，Orchestrator 负责让决策不短视；模型调用只在合规边界内进行，成本通过工程手段控制。

## 3.9 openJiuwen 生态使用说明与部署

> 官方明确：推荐但不强制使用 openJiuwen WorkSwarm / AgentOS；**使用 openJiuwen 生态（WorkSwarm、开源组件、社区工具链）的作品，在评审中将获得"技术方案"维度加分**。本节说明"用了什么、怎么用、哪些自研"，避免"只字未提生态"或"套壳"两种极端。

### 3.9.1 组件映射：复用底座，聚焦方法层

| PromptForge 模块 | 复用的 openJiuwen 能力 | 自研部分 |
|---|---|---|
| Agent 编排与任务规划 | **WorkSwarm** 任务规划、Swarm 协同；**Agent Framework** 多智能体协同与执行引擎 | Prompt DAG 状态机、预算调度策略 |
| 需求编译 Agent | **Agent Studio** 工作流编排、在线调试 | SRD Schema、澄清问题生成与完整性评分 |
| 候选生成 Agent | **Agent Studio** Prompt 调优、在线调试 | 假设矩阵采样、PIR 组装、多样性去重 |
| 执行 Agent | **Agent System Service** 安全隔离沙箱、CLI 工具、标准化文件系统；**Agent Runtime** 分布式执行 | 模型网关适配层、证据包 Schema、执行动作标准化 |
| 评审 Agent | Agent Framework 多 Agent 协同；DeepAgents / JiuwenSwarm 多实例协同 | 盲评/换序协议、偏差校正、BT/Elo 聚合、一致性检验 |
| 决策/融合 Agent | JiuwenSwarm 协同、Agent 自演进（识别轨迹异常、Skills 演进） | TOPSIS/Pareto/HV、集合覆盖/背包、McNemar 回归门 |
| 成本管家 | Agent Framework 算力亲和调度、记忆子系统；WorkSwarm 上下文瘦身 | Token Ledger、UCB/Thompson 预算分配、早停判据 |
| 轻量 Skill 形态 | **WorkSwarm Skills** 自主演进 + **Swarm Skills Hub** 分发 | Skill 的提示词模板与自检规则 |
| 入口与触达 | WorkSwarm **Channel**（小艺/飞书接入）、浏览器操控 | Web 对比看板与会议模式 |

**自研边界（诚实声明）**：PromptForge 不重复实现 Agent 运行时、沙箱、记忆、调度、渠道接入；自研集中在**需求编译（SRD）、证据协议（Evidence Packet）、评审聚合与偏差校正、多准则决策（MCDM）、成本调度、对比可视化**六块——这正是"方法层"的差异化所在。

> 关于"Prompt 自优化"：openJiuwen Agent Studio 已提供 Prompt 调优能力，官方也将"Prompt 自优化"列为生态能力之一。PromptForge 的定位不是"重新发明提示词优化"，而是**在它之上补上"多候选同题竞演 + 执行取证 + 统计决策 + 成本控制"的决策层**；Agent Studio 的 Prompt 调优会作为候选生成策略之一被复用。这个边界写清楚，既拿生态分，也避免"重复造轮子"的质疑。

- **用了什么**：WorkSwarm（规划/Channel/Skills）、Agent Framework（多 Agent 协同）、Agent Studio（Prompt 调优/工作流）、Agent System Service（沙箱）、DeepAgents/JiuwenSwarm（协同）、Swarm Skills Hub（Skill 分发）。

## 3.10 安全、隐私与合规设计

| 风险 | 设计对策 |
|---|---|
| 提示注入（用户输入/仓库内容里藏指令） | 把外部内容当**数据**而非指令；系统提示与用户内容强隔离；执行/评委最小权限；输出 schema 校验；危险工具调用需二次确认 |
| 不可信代码执行 | 沙箱隔离、默认禁网、只读基础镜像、资源配额、超时、无宿主机路径访问；执行日志脱敏 |
| 密钥与凭证 | 环境变量/密钥管理服务，不落库；`.env.example` 占位；演示材料与截图中不出现真实密钥 |
| 数据隐私 | 敏感任务强制本地/专属实例（隐私路由）；可配置脱敏；训练/评测数据来源与许可证声明；不使用未授权数据 |
| 内容安全 | 接入华为云内容安全服务做生成内容审核；交付前扫描 |
| 开源合规 | 获奖作品 Apache-2.0、仓库根目录 LICENSE、README/技术方案/依赖声明/部署指南；**第三方代码 ≤ 有效代码量 30%**；Git 提交历史连续可追溯；第三方依赖逐项列名称/版本/来源/许可证/作用 |
| 比赛合规 | 不使用大赛评测集/测试集训练、调参、设计提示词；演示数据脱敏模拟；不伪造测试数据/演示效果 |
| 滥用风险 | 限流、审计日志、用户可删除数据；对攻击系统、越权访问、恶意代码类请求拒答 |

**红队测试计划**：把"提示注入、越权工具调用、敏感信息泄露、恶意代码执行、评测数据污染"写成 5 组红队用例，纳入 golden set 与回归门（任一回归直接拒绝发布）。

**本节小结**：安全不是附加项，而是"项目运行"评分档位里"卓越且安全的架构"的直接得分点；同时比赛把数据/安全合规设为评审前置条件，任何一项失守都可能一票否决。


# 4. 预期体验（So What）

前面三章讲的是系统"是什么、怎么转"；这一章把机制翻译回人的感受，并给出**可观测的验证指标**，避免"我觉得很好用"式的自嗨。

## 4.1 三类用户与前后对比

| 用户 | 现在怎么做 | 痛点 | 用 PromptForge 之后 |
|---|---|---|---|
| 独立开发者 / 学生 | 想到什么问什么，来回改十几轮 | 不知道提示词差在哪，方案返工多，token 与时间成本不可见 | 输入关键词 → 拿到 3 个带证据的方案与推荐理由，10 分钟内确定方向 |
| 企业研发团队 | 资深工程师手写方案，评审靠经验 | 方案质量依赖个人水平；评审意见难量化；模型供应商锁定 | 多方案对比看板 + 评审报告 + 成本账单，评审会从"拍脑袋"变成"看数据" |
| 非专业"公民开发者" | 不会写提示词，只能套模板 | 需求说不清，AI 输出不可控 | 需求编译器主动澄清、自动补全验收标准，把"不会问"变成"会问" |

## 4.2 分阶段体验

**新手期（0~1 小时）**：零配置。输入一句话，跟着 3 个澄清问题走，默认模板与默认预算即可产出可用结果。体验目标是"第一次就拿到 3 个像样的方案，而不是 1 个半成品"。

**熟练期（1~2 周）**：会调三样东西——候选数量 $N$、评委组合、预算档位；会用"会议模式"投屏对比、给方案打批注、锁定某些假设；会看成本-质量曲线决定"要不要再迭代一轮"。

**精通期（1 个月以上）**：接入团队内部规范与历史项目知识库，自定义评审 Rubric 与权重，接入私有模型/本地推理，把 PromptForge 当成团队的"方案决策基础设施"；对高价值任务使用多轮融合，对低价值任务使用 Skill 单机内循环。

## 4.3 三个典型场景

> 以下为叙事示例（用于说明体验流程），其中的方案数量、耗时与成本均为示意，不是实测数据。

**场景 A：独立开发者（关键词 → 可运行原型）**
输入："做一个校园社团活动报名的网页，能导出名单。" 系统澄清 2 个问题（部署环境？是否需要审核流程？）→ 生成 3 个方案（单体 Next.js / 前后端分离 / Serverless）→ 并行执行并跑测试 → 对比看板显示候选 B 质量更高但成本也更高，候选 A 成本最低且测试全过 → 推荐 A，附 B 的两个优点（审核流程状态机、导出模板）供融合 → 用户点"融合" → 回归测试通过 → 导出仓库 + 提示词 + 报告。

**场景 B：团队方案评审会（把"吵架"变成"看数据"）**
投屏"会议模式"：左侧是候选并排 diff，右侧是雷达图与成本-质量散点；每个争议点标注"证据来源"（测试用例、lint 报告、性能数据）；评委打分不一致的维度高亮显示。团队当场选定方案或指定融合项，系统生成会议决议与版本记录。

**场景 C：IDE 内 Skill（随手的质量提升）**
在 DSH/Codex 里写代码时，输入"把'用户登录'这个需求改写成更好的提示词"，Skill 在单会话内完成：重写提示词 → 自检 4 项 → 若不合格自动再改 1 轮 → 返回改进后的提示词与"为什么这样改"的一句话说明。交互为秒级返回，成本约为单次调用的 1.2~2 倍（估算，待实测）。

## 4.5 可观测指标与验证计划

| 指标 | 定义 | 目标（设计目标，需 A/B 实测校准） | 采集方式 |
|---|---|---|---|
| 一次通过率 | 首次交付即被采纳、不需返工的任务占比 | 较基线提升（幅度以实测为准） | 交付记录 + 用户标记 |
| 平均返工轮数 | 用户要求"再改一版"的次数 | 目标 ≤2 轮（以实测为准） | 会话日志 |
| 方案采纳率 | 推荐的 Top-1 被用户选中的比例 | ≥ 60% | 用户选择记录 |
| 评审一致性 | 多评委 Krippendorff's α | ≥ 0.6 | 评分矩阵计算 |
| 单位任务成本 | 每个任务的 token 费用 | ≤ 同等质量单模型试错的 1.5 倍 | Token Ledger |
| 需求澄清完成率 | 用户完成澄清问答的比例 | ≥ 80% | 交互埋点 |
| 用户主观质量分 | 5 分制满意度 | ≥ 4.0 | 交付后问卷 |

> 验证方法：准备 30 个覆盖代码、文档、多模态的任务集，做 A/B——A 组"直接问一个大模型并人工来回改"，B 组"PromptForge 一次交付"；记录返工轮数、总 token、耗时、人工评分。**以上全部为设计目标，不是当前实测结果；实测数据将记录在附录 G 与 DEMO 报告中。**

## 4.6 设计风险与验证指标

| 风险 | 可能表现 | 观测指标 | 缓解措施 |
|---|---|---|---|
| 评审噪声导致选错方案 | 推荐方案与人工评审结论不一致 | Top-1 与人工评审一致率 | 异构评委 + 位置互换 + 可执行验证占比提高 |
| 多候选成本失控 | 单任务成本超预算 2 倍以上 | 成本/质量曲线、预算命中率 | 预算控制器 + 早停 + 级联评审 |
| 融合导致回归 | 融合后测试通过率下降 | 融合前后测试通过率差 | 融合强制回归 + 失败回退最优单方案 |
| 用户不愿澄清 | 直接跳过问题，SRD 假设错误 | 澄清完成率、假设致返工率 | 每题给默认选项，最多 3 问 |
| 模型 API 不稳定 | 某厂商限流/宕机导致任务卡住 | 任务成功率、降级率 | 多厂商路由 + 备用模型 + 断点续跑 |
| 评委"自我偏好" | 生成某候选的模型给它打高分 | 评分与模型来源的相关性 | 匿名化 + 评委不评自己生成的候选 |
| 演示环境不可控 | 现场网络/沙箱故障 | 演示成功率 | 本地缓存回放 + 录屏兜底 |

**本节小结**：PromptForge 的体验目标不是"一键出神作"，而是**把不确定性前移到"选方案"阶段、把确定性留给"执行验收"**；用户的感受应该是"这次一开始方向就对了"，而不是"AI 又给了我一个看起来不错的半成品"。

## 5.2 技术可行性（按模块）

| 模块 | 依赖的成熟技术 | 成熟度（TRL，评估） | 主要风险 | 备选方案 |
|---|---|---|---|---|
| 需求编译 SRD | 结构化输出、槽位抽取、澄清问答 | 8 | 需求本身不可判定 | 模板 + 人工编辑 |
| 多候选生成 | Prompt 组合、多样性去重、Self-Refine | 8 | 候选同质化 | 反事实候选、假设矩阵强制差异 |
| 模型网关 | OpenAI-compatible API、LiteLLM/vLLM 类方案 | 9 | 厂商 API 变更 | 多厂商适配 + 自建推理 |
| 执行沙箱 | Docker/微虚机、测试框架、Playwright | 9 | 不可信代码安全 | 禁网 + 最小权限 + 快照回滚 |
| 证据采集 | 测试/lint/SAST/性能/截图/ASR/OCR | 9 | 证据维度覆盖不足 | 证据模板可扩展 |
| 多评委聚合 | LLM-as-a-Judge、Bradley-Terry、一致性检验 | 7 | 偏差与噪声 | 异构评委 + 盲评 + 规则评审兜底 |
| 多准则决策 | TOPSIS、Pareto、bootstrap | 9 | 权重主观 | 权重可配置 + 敏感性分析 |
| 融合与回归 | 优点抽取、diff 合并、回归测试 | 6 | 融合冲突/回归 | 只在低耦合优点上融合，失败回退 |
| 预算与停止 | Token 计量、UCB/Thompson、SPRT | 7 | 收益函数估计不准 | 先启发式后自适应，人工兜底 |
| 可视化 | 雷达图/散点/热力图/并排 diff | 9 | 信息过载 | 分层视图（摘要/详情） |
| Skill 形态 | Agent Skills / MCP 工具调用 | 7 | 各 Agent 规范不统一 | 适配层 + 提示词模板降级 |

**结论【推断】**：除了"融合与回归""预算与停止"需要一定实验调参外，其余模块都有成熟工程实践；整体技术风险可控，属于"集成创新"而非"从零发明"，适合比赛周期。

**外部证据**（说明"不是拍脑袋"）：

- 提示词自动优化有效：APE 在 24 个任务中 19 个达到或超过人工指令（[arXiv:2211.01910](https://arxiv.org/abs/2211.01910)）；OPRO 比人工 prompt 在 GSM8K 上 +8%、BBH 上 +50%（[arXiv:2309.03409](https://arxiv.org/abs/2309.03409)）；DSPy 编译后 +25%/+65%（[arXiv:2310.03714](https://arxiv.org/abs/2310.03714)）。前提是"有可自动打分的验证集"，所以 SRD 的验收标准必须可执行。
- 多评委可用但需去偏：GPT-4 评委与人类偏好一致率 >80%（[arXiv:2306.05685](https://arxiv.org/abs/2306.05685)），但位置偏差（[arXiv:2305.17926](https://arxiv.org/abs/2305.17926)）与自我偏好（[arXiv:2404.13076](https://arxiv.org/abs/2404.13076)）真实存在。
- 可执行验证是硬信号：SWE-bench 用真实测试判定补丁（[arXiv:2307.03172](https://arxiv.org/abs/2307.03172)），CodeT 用"生成测试→执行→投票"提升选码（[arXiv:2207.10397](https://arxiv.org/abs/2207.10397)）。
- 风险有据可查：代理指标反复优化会先升后降（[arXiv:2309.17453](https://arxiv.org/abs/2309.17453)）；多智能体辩论成本约 6~9 倍且等算力下收益缩水（[arXiv:2311.17371](https://arxiv.org/abs/2311.17371)）——这两条直接决定了本方案"早停 + 竞演而非辩论"的设计。
- 成本优化手段成熟：级联（[FrugalGPT](https://arxiv.org/abs/2305.05176)）、路由（[RouteLLM](https://arxiv.org/abs/2406.18665)）、压缩（[LLMLingua](https://arxiv.org/abs/2310.05736)）、缓存（[OpenAI Prompt Caching](https://platform.openai.com/docs/guides/prompt-caching)）。

## 5.4 成本可行性

多候选 + 多评委必然比"单模型单轮"贵，关键在于**贵多少、值不值、能不能压**。以下数字来自 3.7 的【算例】（参数为假设值，非实测）：

- 朴素实现（3 候选 × 2 轮 × 4 评委，全部用大模型）在算例参数下约为单模型单轮的 **6.47 倍**（参数为假设值，非实测）；
- 经济档（候选预评审剪枝 + 小模型初评 + 缓存 + 早停 + 按证据难度分配预算）在算例中可压到单轮的 **3~5 倍**，约单模型长跑的 **1.2~1.7 倍**（【推断】，需 A/B 实测；详细模型与算例见 3.7）；
- 若质量收益（返工减少、方案采纳率提升）带来的时间/人力节省超过成本增量，则经济上成立。用 3.5 的决策不等式判断：当 $\Delta Q/Q_{\text{base}} > k\cdot\Delta C/C_{\text{base}}$ 时才值得启用多候选（$k$ 为用户可配置的"质量-成本汇率"）。

> **诚实结论**：对"写个脚本"这类低价值任务，多候选不划算，应默认走 Skill 单机模式；对"方案选型/架构设计/长周期项目"这类高价值任务，多花约 2~5 倍 token 换一次正确的方向，ROI 显著为正。产品必须**按任务价值自动切换档位**，而不是所有任务都开满。

## 5.6 对用户四个原始想法的详细评审

### 想法 1：中转 + 多提示词 + 数学对比 + 可视化 + 融合

**保留，作为作品主线。** 这正是"提示词编译器 + 多方案决策"的核心。需要补三块用户原想法中没有的工程约束：

1. **"中转站"要升级为"带证据的网关"**：只转发没有壁垒，转发 + 执行 + 取证 + 计费 + 审计才有。
2. **"数学模型"要落到可解释的指标与统计**：单纯算一个综合分容易被质疑；需要 TOPSIS/Pareto + 置信区间 + 敏感性分析（见 3.5）。
3. **"融合优点"要工程化**：优点必须先结构化为"可合并单元"，融合后必须回归测试，否则"融合"会变成"缝合怪"。建议一期只融合低耦合优点（测试用例、边界处理、文档、提示词片段），架构级融合放二期。

### 想法 2：机机联动 + 执行结果回读评审

**保留并工程化。** "机机联动"的价值不在"让两个模型聊天"，而在"让执行结果以机器可读形式回到评审环节"。落地重点：

1. **协议而非热情**：LLM→执行模型→证据→评委→优化，每一跳都要有结构化 schema（SRD、Execution Contract、Evidence Packet、Score Card），否则就是"两个黑箱互相猜"。
2. **证据分级**：代码类任务以测试、编译、静态分析、性能为强证据；UI/图表/视频类任务可选"关键帧 + OCR/ASR/元数据"多模态证据（中证据），按需启用（见 3.3.4）。
3. **评审闭环**：多评委基于同一份证据包盲评，评分与证据引用一并留档，形成可复现的优化回路。

### 想法 3：外部 LLM 编排 vs 大模型 Skill

**两者都要，但分工明确。** 用户担心的"头脑（LLM）与身体（大模型）脱节"是真实问题，根因是：目标不一致、上下文不同步、反馈不结构化、责任边界不清。解法是**双形态 + 单一事实源 + 协议化**（见 3.8）：

- **Skill** 解决"单会话内、低延迟、低成本"的自迭代，让执行端不再"无脑"；
- **Orchestrator** 解决"跨模型、多方案、可审计、带预算"的决策；
- 两者用 SRD/Evidence 共享状态，执行端回传证据，编排器只做仲裁。

**模型获取与成本**：所有模型调用走官方 API/云服务或本地部署；"人人用得起"通过模型路由、缓存、批处理、本地小模型与按任务价值分档实现。

### 想法 4：Token 成本优化

**保留并升级为核心卖点。** 用户担心"来回联动导致成本追平集群模式"，这个担心合理，但结论不是"少联动"，而是"**会算账地联动**"：Token Ledger 计量 + 预算分配 + 早停 + 剪枝 + 级联 + 缓存 + 蒸馏。要敢于在答辩中给出"成本-质量"曲线，而不是只讲功能。

## 5.7 八条可执行优化建议

1. **先做窄场景**：一期只做"Web/脚本类代码任务"，把证据链做深，不追求全品类。
2. **把"证据"做成产品壁垒**：同样的多方案对比，别人给评分，你给"测试通过率 + lint + 性能 + 可复现哈希"。
3. **评委异构化**：至少覆盖 3 家不同厂商模型 + 1 个规则评审，避免"同源模型互相吹捧"。
4. **预算档位化**：经济/标准/深度三档，默认经济档，按任务价值自动推荐。
5. **融合保守化**：只融合可验证的低耦合优点，架构级融合必须有回归测试与人工确认。
6. **把 Skill 作为获客入口**：轻量、免费/低成本，让用户先感受到"提示词变好了"，再引导到 Orchestrator。
7. **数据闭环**：记录用户最终采纳与修改，反哺权重与 Rubric（注意隐私与授权）。
8. **讲一个可验证的故事**：比赛材料里放"同一任务：传统方式 N 轮 vs PromptForge 2 轮"的对照实验，比讲架构更有说服力。

| 模板量规·对现实世界的影响 | "让每个开发者请得起 AI 专家评审团" | 4/5 | 用一个用户故事讲影响 |
| 模板量规·主题一致性 | 多智能体协同（智体共生）+ 现实场景创新应用 | 4~5/5 | 封面第一页就点题 |

**最大的竞赛风险**：创意阶段只有 PPT、没有可运行 DEMO 时，容易被评为"想法大、实现少"。对策：**11-10 前必须完成"可运行的最小闭环"并录屏**（哪怕只支持 1 个模型 + 2 个候选 + 规则评审），把"项目运行"这一档先拿到 3 分以上，再在 DEMO 阶段冲 4~5 分。详见 §7.2。

**本节小结**：四个想法中，1 和 4 直接保留为产品核心，3 用"双形态"化解，2 的"机机联动 + 执行结果回读"保留并工程化；整体技术可行、工程可控、合规风险可通过取舍规避。按官方赛程与评审维度倒排，本作品在 10-31 报名截止、11-10 创意提交、12-27 DEMO 截止的节奏下具备可交付性，最大风险是"创意阶段缺可运行证据"，已用"11-10 前最小闭环 + 录屏"的对策覆盖。


# 6. 创新点与差异化

## 6.1 四个创新点

**创新点 1：证据驱动的多方案决策（Evidence-based Portfolio Decision）**
现有提示词工具优化的是"文本"，PromptForge 优化的是"决策"：每个候选必须真正执行并产出可验证证据（测试、lint、性能、安全扫描、截图），评委只能在证据上打分，最终用 TOPSIS/Pareto 做多准则决策，并给出置信区间。把"哪个提示词更好"从主观判断变成可复现的测量。这套思路有直接的技术依据：SWE-bench 用仓库真实测试判定补丁是否有效（[arXiv:2307.03172](https://arxiv.org/abs/2307.03172)），CodeT 用"生成测试→双执行→投票"低成本提升选码质量（[arXiv:2207.10397](https://arxiv.org/abs/2207.10397)）；而"重复采样能提升覆盖率、但没有可靠验证器就无法兑现收益"的结论（[arXiv:2407.21787](https://arxiv.org/abs/2407.21787)）恰恰说明：**验证器/选择器才是瓶颈，也是本方案的壁垒**。

**创新点 2：异构多评委 + 偏差校正 + 统计收敛**
不是"让 LLM 打个分"，而是把 LLM-as-a-Judge 做成可审计的评审系统：评委来自不同厂商/规模、匿名盲评、位置互换、长度/自我偏好校正、一致性检验，低一致性时自动增加评委或转人工仲裁。依据：MT-Bench 的"LLM 评委与人类偏好一致率超过 80%、与人类-人类一致率同量级"（[arXiv:2306.05685](https://arxiv.org/abs/2306.05685)）；G-Eval 的 CoT + 表单式评分（[arXiv:2303.16634](https://arxiv.org/abs/2303.16634)）；但位置偏差（[arXiv:2305.17926](https://arxiv.org/abs/2305.17926)）与自我偏好（[arXiv:2404.13076](https://arxiv.org/abs/2404.13076)）真实存在，必须用换序双评与跨家族评委消除。

**创新点 3：成本感知的自适应编排（Token is a Budget）**
把 token 当作一等公民：Token Ledger 全链路计量、预算分档、边际收益驱动的候选数量选择、级联评审、早停与剪枝。系统能回答"再迭代一轮值不值"，并在预算耗尽前给出当前最优解。依据：级联可显著降本（FrugalGPT，[arXiv:2305.05176](https://arxiv.org/abs/2305.05176)）；路由可在质量不降的前提下降低 2 倍以上成本（RouteLLM，[arXiv:2406.18665](https://arxiv.org/abs/2406.18665)）；缓存与批处理是厂商已提供的确定性折扣（[OpenAI Prompt Caching](https://platform.openai.com/docs/guides/prompt-caching)）；而"反复用评委分数选优会导致代理指标先升后降"（[arXiv:2309.17453](https://arxiv.org/abs/2309.17453)）说明必须早停并把可执行验证混入目标函数。

**创新点 4：双形态架构（Orchestrator + Skill）与单一事实源**
解决用户原始想法 3 中"头脑与身体脱节"的问题：执行端用 Skill 做单会话自迭代，编排器做跨模型决策，二者通过 SRD/Evidence 共用同一份事实，避免"外部 LLM 瞎指挥、执行模型闷头干"。协议层可直接站在成熟标准上：OpenAI function calling 负责单次工具调用（[OpenAI](https://openai.com/index/function-calling-and-other-api-updates/)），MCP 负责工具/资源接入（[MCP 架构](https://modelcontextprotocol.io/specification/2026-07-28/architecture/index.md)），A2A 负责 Agent 间任务委派（[a2a-protocol.org](https://a2a-protocol.org/latest/)），Agent Skills 负责能力打包分发（[Anthropic Skills](https://claude.com/blog/building-agents-with-skills-equipping-agents-for-specialized-work)），而不是自造协议。

## 6.2 与相关产品/方案的差异

| 类别 | 代表产品/方案 | 它们擅长什么 | 它们的空位 | PromptForge 的差异 |
|---|---|---|---|---|
| 提示词优化器 | PromptPerfect（Jina AI）等单点工具 | 把一句话改写成更详细的提示词 | 不知道执行结果，无证据、无多方案对比；单点工具易被平台能力吞并 | 用执行证据闭环，多候选假设对比 |
| 提示词管理/观测 | PromptLayer、LangSmith | 版本管理、调用日志、评测数据集 | 面向"已有提示词"的观测，不解决"从关键词到方案"的决策 | 从需求编译开始，产出可交付方案与决策报告 |
| 模型网关/聚合 | OpenRouter、LiteLLM、OneAPI/New API | 统一接口、转发、计费、路由 | 只转发不决策 | 网关之上有编译、竞演、评审、决策（网关可直接复用成熟方案，不自研） |
| Agent 应用平台 | Coze/扣子、Dify、华为云 AgentArts | 低代码搭 Agent/工作流，有编排与基础观测 | 单一路径执行，缺"多候选同题竞演 + 可审计 MCDM 决策" | 多方案并行 + 评审团 + 统计决策 + 交付包 |
| 编码 Agent | GitHub Copilot、Cursor、Windsurf、Devin、华为云码道 | 在 IDE/云端完成编码任务 | 用户只拿结果，看不到"多模型同题对比 + 评分证据"，返工靠人 | 可作为它们的"上游方案编译器 + 下游评审台"，也可 Skill 内嵌 |
| 模型排名/评测 | LMArena、Braintrust | 模型排名、应用评测 | 只给分数与排名，不闭环到"为当前任务交付最佳方案" | 从"评测"走到"决策 + 交付 + 复盘" |
| 多智能体辩论框架 | 各类 MAD 实现 | 多角色讨论提升部分推理任务 | 成本约 6~9 倍调用量，等算力下收益缩水；易跑题 | 不做无限辩论，做有预算、有证据、可复现的决策 |

**差异化一句话**：别人优化"提示词"，我们优化"从需求到方案的决策质量"；别人比"模型分数"，我们比"可执行证据 + 成本 + 置信度"。

## 6.3 关键设计决策与技术依据对照

| 设计决策 | 技术依据 | 对方案的约束 |
|---|---|---|
| 先写验收标准，再生成提示词 | APE 在 24 个任务中 19 个达到/超过人工指令（[arXiv:2211.01910](https://arxiv.org/abs/2211.01910)）、OPRO 比人工 prompt +8%（GSM8K）/+50%（BBH）（[arXiv:2309.03409](https://arxiv.org/abs/2309.03409)）、DSPy 编译 +25%/+65%（[arXiv:2310.03714](https://arxiv.org/abs/2310.03714)）——这些方法都以"可自动打分的验证集"为前提 | SRD 的验收标准必须可执行；没有验证集时不能宣称"自动优化" |
| 多候选并行 + 确定性验证，而非多智能体辩论 | 辩论有提升但成本约 6~9 倍（[arXiv:2305.14325](https://arxiv.org/abs/2305.14325)）；等算力预算下未必优于 self-consistency（[Should we be going MAD?](https://arxiv.org/abs/2311.17371)） | 默认并行候选 + 验证器；辩论仅用于高风险子项且受预算约束 |
| 多评委 + 换序 + 跨家族 + bootstrap CI | LLM 评委与人类一致率 >80%（[arXiv:2306.05685](https://arxiv.org/abs/2306.05685)），但存在位置/长度/自我偏好偏差（[arXiv:2305.17926](https://arxiv.org/abs/2305.17926)、[arXiv:2404.13076](https://arxiv.org/abs/2404.13076)） | 任一评委不得评自己生成的候选；分差落在 CI 内不强行排序 |
| 早停 + 验证信号混合 | 代理指标优化会先升后降（[arXiv:2309.17453](https://arxiv.org/abs/2309.17453)） | 迭代最多 3 轮；测试/编译等硬信号优先于评委分 |
| 网关复用而不自研 | LiteLLM 支持 100+ 模型统一为 OpenAI 格式 + 路由/预算/成本追踪（[GitHub](https://github.com/BerriAI/litellm)）；RouteLLM 证明路由降本 2×+（[arXiv:2406.18665](https://arxiv.org/abs/2406.18665)） | 自研聚焦上层决策，网关用成熟开源或本地推理 |
| 结构化输出 + 工具调用 | OpenAI Structured Outputs 保证 schema 合法（[OpenAI](https://openai.com/index/introduction-to-structured-outputs/)）；但 schema 不保证语义正确 | 证据必须来自执行与测试，评委不得只看 JSON 格式 |
| 长上下文压缩 | LLMLingua 最高 20× 压缩（[arXiv:2310.05736](https://arxiv.org/abs/2310.05736)） | 对超长证据包做摘要/压缩后再给评委，压缩率与保真度需实测 |

## 6.4 与"多智能体辩论"的边界

用户原始想法 2 接近"让多个 LLM 来回讨论、互相审查"，这在学术上对应 Multi-Agent Debate。我们的取舍是：**不做开放式辩论，做"并行竞演 + 确定性验证 + 统计评审"**。原因：

1. 辩论的成本随 agent 数 × 轮数线性放大（3 agents × 2~3 轮 ≈ 6~9 倍调用量），而等算力预算下收益可能被 self-consistency 追平（[arXiv:2311.17371](https://arxiv.org/abs/2311.17371)）；
2. 辩论容易"跑题/趋同"，而代码任务的真相在测试与编译器里，不在讨论里；
3. 比赛与产品都需要可复现、可解释的决策过程，辩论的中间状态难以审计。

因此辩论仅作为**高风险子项的可选环节**（如架构选型争议），且必须受预算与轮数控制。

## 6.5 与 openJiuwen 生态的关系

openJiuwen 已经提供了完整的 Agent 运行时与工具链，这正是本作品的机会——**不自建重复能力，而是补上"方法层"**：

| openJiuwen 能力（官方 FAQ/官网口径） | 我们的复用方式 | 我们不重复做的事 |
|---|---|---|
| **WorkSwarm**：任务规划、自演进、上下文瘦身、记忆随行、Channel（小艺/飞书） | 作为 Agent 运行与入口层；用其 Skills 机制承载轻量 Skill 形态 | 不自研 Agent OS、不重写渠道接入 |
| **Agent Framework**：多智能体协同、自演进、记忆子系统、算力亲和调度 | 用多 Agent 协同承载候选生成/执行/评审/决策；用记忆子系统沉淀项目知识 | 不自研调度引擎 |
| **Agent Studio**：低代码工作流、Prompt 调优、在线调试 | 复用 Prompt 调优作为候选生成策略之一；用工作流编排需求编译与评审流程 | 不重复做 Prompt 调优 |
| **Agent System Service / Agent Runtime**：安全隔离沙箱、统一记忆、CLI 工具、标准化文件系统、跨 Agent 通信 | 执行沙箱与工具调用的底座 | 不自研沙箱与运行时 |
| **DeepAgents / JiuwenSwarm**：多实例协同、DeepSearch 等 | 高风险子项的协同辩论（受预算控制）、资料检索 | 不做通用的多智能体框架 |
| **Swarm Skills Hub** | Skill 形态的分发与复用 | 不自建技能市场 |

**我们的差异化（选题意义上的"补位"）**：openJiuwen 生态有"执行与协同"，但"从关键词到可审计决策"的方法层仍缺——**需求编译（SRD）、证据协议（Evidence）、异构评审去偏、TOPSIS/Pareto 决策、Token 预算调度**这五件是我们的自研重点，也是"技术方案"维度最能拿分的地方。这个分工在 §3.9 有组件级说明。

**结论【推断】**：对评审而言，这既证明"真的用了生态"（拿生态加分），又证明"不是套壳"（有自研方法层）；两者结合比"全部自研"或"全部套壳"都更稳。

**本节小结**：PromptForge 的新颖性不在"用了 LLM"，而在**把提示词工程升级为可验证、可决策、可计费的工程流程**；技术依据充分、边界清晰（辩论改为竞演、证据优先、网关复用不自研、生态复用不套壳），对比赛而言是一个"技术深度 + 应用价值 + openJiuwen 生态"都能讲通的故事。

# 8. 答辩预演：评委可能问的问题

## 8.1 高频问题与回答要点

**Q1：这和"让大模型自己优化提示词"有什么区别？**
A：单模型的 self-refine 是"同一条思路上的自我修改"，容易陷入局部最优且没有外部证据；PromptForge 是"多个不同假设的方案并行执行 + 用测试/指标取证 + 异构评委盲评 + 统计决策"，本质是把"提示词优化"变成"方案决策"。我们不做无限自我反思，做有预算、有证据的择优。

**Q2：多个 LLM 评审可靠吗？会不会互相吹捧或随便打分？**
A：不可靠的单评委确实有偏差，所以我们做了四件事：评委异构（不同厂商/规模）、匿名盲评 + 位置互换、长度/自我偏好校正、一致性检验（Krippendorff's α，低于阈值自动加评委或转人工）。同时把"可执行证据"作为强信号，LLM 评分只占部分权重。最终输出带置信区间，而不是一个绝对分数。

**Q3：多方案多评委，成本会不会翻好几倍？**
A：在 3.7 的算例参数下，朴素实现约为单轮的 6 倍以上；但更公平的对照是"单模型 self-refine 长跑"，算例中我们约为它的 2.16 倍；再叠加候选剪枝、弱评委、缓存、早停，经济档在算例中可压到单轮的 3~5 倍（约长跑的 1.2~1.7 倍）。上述均为【算例】或【推断】，实际倍数需用真实报价与实测 token 校准（见附录 G）。系统会算"再迭代一轮值不值"，在预算耗尽前输出当前最优；对低价值任务默认走 Skill 单机模式，成本约为单次调用的 1.2~2 倍（估算）。

**Q4：为什么用 openJiuwen 生态？是不是套壳？**
A：我们复用的是它已经成熟的"运行时/沙箱/协同/渠道/技能分发"（WorkSwarm、Agent Framework、Agent Studio、Agent System Service），自研的是它当前不覆盖的"决策层"：需求编译（SRD）、证据协议、评审去偏、TOPSIS/Pareto 决策、Token 预算调度。生态是地基，方法是壁垒——这既符合官方"用生态加分"的规则，也不是套壳。组件级说明见 3.9。

**Q5：你们怎么保证评审数据与效果数据不注水、不造假？**
A：三条机制：① 所有指标在实验前登记（指标定义、任务集版本、模型版本、参数），不做"看到结果再改指标"；② 每次评分保留原始日志（模型、token、价格、耗时、评委原始分、位置顺序），交付包可回放；③ 对外只引用台账中已实测的数据，标【算例】【推断】【设计目标】的绝不写成"实测结果"；DEMO 阶段提供可复现实验脚本与原始记录，欢迎评委抽查。数据台账见附录 G。

**Q6：图像/视频这类多模态任务怎么评审？**
A：不把原始媒体直接送入模型，而是走"多模态证据通道"：关键帧/截图交多模态模型理解；OCR/ASR/ffprobe/UI 自动化等本地工具提取结构化字段（字幕、元数据、界面差异）；结构化结果写入 Evidence Packet，作为"中证据"参与评审。代码类任务仍以测试、编译、静态分析等强证据为主。该能力为可选模块，默认关闭，仅在任务确实涉及 UI/图表/演示内容时启用（详见 3.3.4）。

**Q7：如果所有候选都很差怎么办？**
A：先做"候选预评审门禁"，避免用贵流程筛烂提示词；若全部不合格，回到需求编译，检查 SRD 是否不可执行或目标过高；必要时降级为 MVP 拆解，而不是继续堆提示词。系统会把失败原因写入交付包，方便复盘。

**Q8：融合多个方案的优点，会不会变成"缝合怪"？**
A：会，所以我们只融合低耦合优点（测试用例、边界处理、文档、提示词片段），架构级融合放二期；融合后用 McNemar 检验做显著性判断，不显著就不宣称融合更好，并强制全量回归测试，不通过就回退到最优单方案。融合不是必选项。

**Q9：和 Cursor/Copilot/Devin 是什么关系？**
A：它们是把任务做出来的"执行器"，我们更像执行器上层的"方案编译器 + 评审台"。我们可以把优化后的提示词与验收标准交给它们执行，也可以以 Skill 形式内嵌；不替代 IDE，而是让 IDE 里的 AI 一开始就方向正确。

**Q10：商业价值在哪里？**
A：三层：个人开发者按次/订阅（低成本档）；企业团队私有化部署 + 内部规范知识库（高客单）；API/平台化（把"方案决策"能力输出给其他 Agent 平台）。核心指标是"减少的返工时间与 token 成本"，可直接折算 ROI。

**Q11：你们怎么证明效果？**
A：30 个任务的 A/B 对照：传统方式（直接问一个大模型 + 人工来回改）vs PromptForge 一次交付，记录返工轮数、总 token、耗时、人工评分；同时报告评委一致性与推荐采纳率。所有数字来自实际记录，答辩时展示原始日志。

**Q12：获奖后要开源，会不会被人抄？**
A：比赛规则要求获奖作品 Apache-2.0 开源，我们接受这个规则并把壁垒放在"数据闭环 + 团队知识库 + 方法迭代"上，而不是代码保密；开源反而有利于生态集成与获客。

**Q13：最大的技术风险是什么？**
A：评审噪声与融合回归。应对：提高可执行证据权重、异构评委 + 一致性门槛、融合强制回归 + 回退策略。我们宁愿"保守地推荐一个稳的方案"，也不"激进地推一个没验证过的融合体"。

## 8.2 三类叙事版本

- **30 秒版**：输入一句话，PromptForge 生成多个不同假设的方案，真正跑起来、拿证据、由多个不同厂商的模型盲评，最后用数学模型选出最优并给出成本账单——让 AI 开发从"反复试错"变成"一次选对"。
- **3 分钟版**：在 30 秒版基础上加"为什么难"（提示词质量方差大、单模型自评有偏差、多方案成本高）与"我们怎么解"（SRD 编译、证据回读、异构评审、预算调度、双形态、openJiuwen 生态）。
- **电梯版（一句话）**：**PromptForge 是 AI 开发者的"方案编译器 + 评审会"，让每个开发者都请得起一个由多个模型组成的专家评审团。**

**本节小结**：答辩的核心不是证明"我们技术最先进"，而是证明"我们想清楚了边界"——知道什么可行、什么不可行、成本多少、风险在哪、生态用什么补什么，并且有可演示的闭环与真实数据。

### A.1 TOPSIS 算例（4 候选 × 5 指标，权重取均衡预设，数值人为构造）

原始矩阵与计算步骤见 3.5.2。关键中间结果：

| 候选 | 向量归一化后正确性 | 加权后成本 | $D^+$ | $D^-$ | 贴近度 $C^*$ | 排名 |
|---|---|---|---|---|---|---|
| A | 0.4927 | 0.0918 | 0.042011 | 0.046055 | 0.522960 | 3 |
| B | 0.5408 | 0.1257 | 0.069249 | 0.046328 | 0.400841 | 4 |
| C | 0.4447 | 0.0628 | 0.053533 | 0.069303 | **0.564189** | **1** |
| D | 0.5168 | 0.1088 | 0.049675 | 0.054979 | 0.525343 | 2 |

**结论**：C > D > A > B；但 A 与 D 差 0.0024（0.46%），低于噪声，须 bootstrap 秩稳定性或并列进下一轮；C 若正确性硬门槛 ≥80 则先被过滤。

### A.2 Pareto / HV 与 SAW 对比

- **HV**：非支配集 {E(30,0.80), G(40,0.84), F(45,0.86), H(55,0.88)}，参考点 (60,0.75)，$HV=2.70$；新增 K(42,0.87) 支配 F 后 $HV'=2.89$，**ΔHV=+7.04%**。
- **SAW vs TOPSIS 反例**：X=(10,10,1)、Y=(6,6,6)，等权 3 指标；SAW 归一化 X=0.667 > Y=0.333，TOPSIS $C_X=0.371 < C_Y=0.629$——两法可给出相反排序，方法选择必须写明价值取向。

### P2 创意名称 / 创意描述 / 所属主题 / 应用场景

**创意描述（<500 字，建议定稿版）**

> PromptForge 是面向 AI 开发者的"提示词编译器 + 多智能体评审会"。用户输入关键词或一句话需求，系统先把它编译成含可执行验收标准的方案规格（SRD），再生成 3~5 个"假设不同"的候选提示词，调用多个大模型（Pangu/Qwen/DeepSeek 等）并行执行，自动采集测试、静态分析、性能、截图等机器可读证据；随后由多个不同厂商的 LLM 评委匿名盲评 + 规则验证，用 TOPSIS/Pareto 与置信区间选出最优方案并生成对比看板；最后支持"优点融合 + 回归验证"，输出可复现的交付包与成本账单。它解决三个问题：需求说不清、方案选不对、结果没验证。相比单模型自我反思，它用执行证据和异构评审取代主观自评；相比单点提示词工具，它从"改句子"升级为"做决策"，并用 Token 预算调度把多方案成本压到可接受范围。

**所属主题**：Coding

**应用场景（<500 字，建议定稿版）**

> 面向独立开发者、高校学生与 2~20 人的研发团队：从一句话想法做原型、技术方案选型、评审会决策、AI 生成代码的验收。典型场景：开发者输入"做一个带登录的待办事项 Web 应用"，PromptForge 主动澄清 2 个关键问题，生成 3 个不同架构假设的方案并真实执行，10 分钟内给出"推荐方案 + 次优备选 + 成本账单 + 证据链"。用户潜在需求：不想把时间花在反复改提示词和返工上、希望 AI 生成结果可解释可复现、希望团队评审有数据而不是拍脑袋。对垂直领域的影响：把"提示词工程"升级为可审计的"方案决策工程"，让中小团队也拥有过去只有大厂才有的多方案评测能力；对个人开发者，它降低了与 AI 协作的专业门槛，让"问得对"不再依赖个人经验。

## G.4 对外表述与变更规则

- 对外材料（PPT/视频/答辩/README）引用数字时，必须同时能指出其台账 ID 与级别（事实/实测/算例/目标/推断）。
- 实测数据只有写入台账并附原始日志后，才允许对外表述为"实测/验证"。
- 文档变更：任何影响范围、成本、指标的修改，需更新台账与修订记录；重大架构决策另记 ADR（见《实施工作台》）。
- 若发现既往表述与数据不符，立即更正并在修订记录中说明，不静默修改。
